# レビュー生成パイプライン（review-full-pipeline）

対象スキー場について、3フェーズを**順番に**実行する。

`review-research-detail` / `review-verify-detail` / `review-write-article` の3つは
いずれも frontmatter に `context: fork` が設定されている。これにより、`Skill` ツールで
名前を指定して呼ぶだけで、そのSkillは**自動的に**独立したサブエージェントとしてフォークされ、
SKILL.md の内容そのものがサブエージェントへの初期プロンプトになる（保証された動作）。
このSkill（review-full-pipeline）自身が `Agent` ツールを直接呼ぶ必要はない。

## 入力

スキー場名とスラッグ、および**ユーザーの依頼文に含まれる、対象の識別・絞り込みに関わる情報すべて**（例: 「似た名前の別施設・別エリアと混同しないでほしい」「〇〇とは別のスキー場」
「正式名称は△△だが一般には□□と呼ばれている」など）。スラッグ未指定なら、正式名称から
適切な英字スラッグを決めてユーザーに確認してから次に進む。

**最重要の注意:** `review-research-detail` / `review-verify-detail` / `review-write-article` は
`context: fork` で実行されるため、フォークされたサブエージェントが受け取れる情報は
各Skill呼び出し時に渡す `args`（`$ARGUMENTS` に置換される）**だけ**である。この会話で
ユーザーから得た背景情報・注意点・曖昧さの解消説明は、`args` に明示的に含めない限り
サブエージェントには一切伝わらない。「スキー場名とスラッグだけ」のように要約して渡すと、
ユーザーが与えた重要な注意点が失われる。

## 実行手順

必ずこの順番で、**前のフェーズの完了を待ってから**次を呼ぶ（並列不可）。
フェーズ2はフェーズ1が作成した`detail.md`を、フェーズ3はフェーズ2で検証済みの
`detail.md`を前提とするため、依存関係を守る。

1. **フェーズ1（調査）** — `Skill` ツールで `review-research-detail` を呼ぶ。
   `args` には、スキー場の正式名称・スラッグに加えて、**ユーザーの依頼文にある識別・絞り込み
   情報を要約せず含める**（例: `"スキー場名: 志賀高原中央エリア, スラッグ: shiga-kogen-central。
   注意: 志賀高原の焼額山・奥志賀・横手山・熊の湯とは別のスキー場として扱うこと。それらの
   情報を志賀高原中央エリアのレビューとして混同しないこと。"`）。
   `context: fork` により自動的に独立したサブエージェントとして実行される。完了を待つ。
2. **フェーズ2（検証）** — フェーズ1完了後、`Skill` ツールで `review-verify-detail` を呼ぶ。
   `args` にスラッグと、フェーズ1同様の識別・絞り込み情報（あれば）を渡す。完了を待つ。
3. **フェーズ3（記事化）** — フェーズ2完了後、`Skill` ツールで `review-write-article` を呼ぶ。
   `args` にスラッグを渡す。完了を待つ。

## 途中で問題が起きた場合

いずれかのフェーズが失敗・ブロックした場合は、そこで停止してユーザーに状況を報告する。
無理に次のフェーズへ進めない。

## 完了報告

3フェーズすべて完了後、各フェーズの完了報告を統合して、以下をユーザーに伝える:

- 作成・修正した全ファイルの一覧（`detail.md` / `article.md` / `full_article.md`）
- 独立ソース総数、カテゴリごとの確度傾向（フェーズ1の報告より）
- 検証で修正した内容（フェーズ2の報告より）
- 各カテゴリの評価（◎/○/△）（フェーズ3の報告より）
- 判断を保留した内容、人間による確認を推奨する箇所
