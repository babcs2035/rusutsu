# 旧称・ふりがなの編集と、AIで作ったレビューの公開

旧称・ふりがなは管理画面で編集します。レビューはこれまでどおりJSONを作り、完成後に本番へ送ります。
Gitへのpushは、レビューの公開操作にはなりません。

## 最初に一度だけ行うこと

この修正をmainへ反映してCI/CDを成功させます。通常のDBマイグレーションで、既存のスキー場に対応する旧称・ふりがなを移行します。
移行には506件分の辞書を固定して収録しています。`INITIALIZE_CANONICAL_DATA`を再びtrueにする必要はありません。
ローカルも最新コードに揃え、`mise run setup`でローカルDBの構造を更新してください。

移行後はJSONの変更を自動取り込みしません。管理画面で削除した旧称や読みが、次のデプロイで元に戻ることもありません。

## 旧称・ふりがなを変更する

1. 本番サイトの`/rusutsu/admin/resort`へアクセスしてログインします。
2. 対象のスキー場を選び、「ふりがな・旧称」を編集します。
3. ふりがなは左に名前の一部分、右にその読みを入れます。例えば「山／やま」「スキー場／空欄」です。
   左の文字を順番につなげると「名称（日本語）」になるようにします。
4. 旧称は「旧称を追加」で増やせます。不要なものはその行を削除します。
5. 画面の保存ボタンを押し、公開画面を再読み込みして、表示と検索を確認します。

編集はDBへ保存され、Gitへのpushや再デプロイは不要です。`SkiResortReadings.json`はアプリの実行時には読みません。

ふりがなはJSONを丸ごとDBへ入れる方式ではありません。「スキー場ID・表示順・対象の文字・読み」を列に持つ専用テーブルへ保存します。
旧称も「スキー場ID・表示順・名前・読み」を列として保存します。存在しないスキー場への登録や同じ順番の重複はDBの制約でも防ぎます。

## 普段のレビュー制作：AIに作成から反映まで頼む

今までどおり、次の2ファイルを用意します。

```text
src/private/data/reviews/スキー場ID/detail.json
src/private/data/reviews/スキー場ID/article.json
```

ChatGPTでdetail.jsonを作り、CodexやClaude Codeでarticle.jsonを作る流れは変わりません。
その後、例えば次のように依頼できます。

> このスキー場のdetail.jsonとarticle.jsonを検証し、本番との差分を確認して、問題がなければ本番へ反映してください。

担当AIは下のコマンドで差分を確認し、反映を実行できます。キーを毎回チャットに貼る必要はありません。
「記事を書いて」という依頼だけでは、本番公開まで指示したことにはなりません。

### Macの設定（初回のみ）

プロジェクト直下の`.env.local`に、既存の管理用キーを設定します。

```dotenv
DATA_API_BASE_URL="https://実際の本番ドメイン/rusutsu"
INTERNAL_DATA_API_ADMIN_TOKEN="GitHub Secretsに登録した管理用キー"
```

専用コマンドはAPIへ直接通信するため、ローカルの開発サーバーやDBを起動する必要はありません。
依存ライブラリは通常のセットアップで準備します。

### コマンドを自分で実行する場合

最初は差分確認です。`rusutsu-resort`は実際の対象IDに置き換えてください。

```bash
mise run reviews:publish -- --resort rusutsu-resort
```

ここでは保存しません。2ファイルの検証と、本番の現在値との比較を行います。
確認内容は`.review-publication-plan.json`に保存されます。このファイルにはAPIキーを含めず、Gitにも登録しません。

内容がよければ、同じコマンドに`--apply`を追加します。

```bash
mise run reviews:publish -- --resort rusutsu-resort --apply
```

プレビュー後にJSONや接続先が変わっていたら停止します。本番が他の人に更新されていても停止します。
その場合は、本番の変更を取り込んでJSONを見直し、最初の差分確認からやり直します。
成功すると2ファイルが一緒に保存されます。片方だけの反映にはなりません。

複数のスキー場を並行作業する場合は、`--plan /tmp/スキー場ID-review-plan.json`など別々の保存先を指定し、
反映時にも同じ`--plan`を指定してください。プランは非公開の作業ファイルとして扱います。

## 手動で行いたいとき：管理画面で2ファイルを選ぶ

1. 本番の`/rusutsu/admin/review`を開き、「作成したJSONを取り込む」を押します。
2. 同じスキー場の`detail.json`と`article.json`を、2つまとめて選びます。
3. 対象IDと、それぞれの「現在の内容」「保存する内容」を確認します。
4. 「確認した2ファイルを保存する」を押します。
5. レビュー編集画面へ戻り、公開画面も再読み込みして内容を確認します。

新規レビューにも対応します。スキー場自体はマスターに登録されている必要があります。

従来のgood/bad形式と、AI制作で使うreason/fullの箇条書き形式に対応します。JSONの形式や調査の証拠を勝手に書き換えて保存することはありません。
箇条書き形式のレビューは、一覧の「AIで作成した形式のレビュー」から現在のJSONを確認し、更新した2ファイルを取り込めます。
文章の事実確認や文体のチェックは制作時のスキルで行ってください。公開処理は形式・対象ID・更新競合などを検証します。

既存JSONの確認では、`naeba`に形式の不一致、`osorakan-snow-park`と`rusutsu-resort`にフォルダー名とJSON内の対象IDの不一致が見つかっています。
これらは自動修正せず、対象のスキー場と内容を確認してから反映してください。
各ファイルは2 MiB以内です。本番APIに接続したローカル管理画面でも使えます。
管理画面の場合はGoogleログインを使うため、ブラウザーにAPIキーを入力する必要はありません。

## JSONとGitはどう使い分けるか

| 場所 | 役割 |
| --- | --- |
| MacのJSON | AIによる調査・記事作成・内容確認の作業場所 |
| rusutsu-library | 調査資料と制作履歴の保管。pushだけで本番DBは更新しない |
| 本番DB | 公開中の内容。管理画面または反映コマンドで更新 |

サーバーで直接編集した内容がMacのJSONへ自動で戻るわけでもありません。
古いJSONを反映する前には必ず差分を確認し、残すべき本番の変更を取り込んでください。

今回の取り込み画面と反映コマンドはレビュー専用です。リフト券料金のJSON取り込みには使いません。
リフト券料金は既存の管理画面で編集・保存できますが、外部で作成した新しい料金JSONを一括で取り込む導線は別途対応が必要です。

`private/data`全体は削除できません。名寄せ辞書・気象関連の辞書・過去の取得結果・初回移行用データなど、
他にも使用中のファイルがあります。今回の旧称・ふりがなのDB化は、全ファイルの削除を可能にする変更ではありません。
