# 旧称・ふりがなの編集と，AI で作ったレビューの公開

旧称・ふりがなは管理画面で編集する．レビューはこれまでどおり JSON を作り，完成後に本番へ送る．
Git への push は，レビューの公開操作にはならない．

## 旧称・ふりがなを変更する

1. 本番サイトの `/rusutsu/admin/resort` へアクセスしてログインする．
2. 対象のスキー場を選び，「ふりがな・旧称」を編集する．
3. ふりがなは左に名前の一部分，右にその読みを入れる．例えば「山／やま」「スキー場／空欄」とする．
   左の文字を順番につなげると「名称（日本語）」になるようにする．
4. 旧称は「旧称を追加」で増やせる．不要なものはその行を削除する．
5. 画面の保存ボタンを押し，公開画面を再読み込みして，表示と検索を確認する．

編集は DB へ保存され，Git への push や再デプロイは不要である．`SkiResortReadings.json` はアプリの実行時には読まない．

ふりがなは JSON を丸ごと DB へ入れる方式ではない．「スキー場 ID・表示順・対象の文字・読み」を列に持つ専用テーブルへ保存する．
旧称も「スキー場 ID・表示順・名前・読み」を列として保存する．存在しないスキー場への登録や同じ順番の重複は DB の制約でも防ぐ．

## 普段のレビュー制作：AI に作成から反映まで頼む

今までどおり，次の 2 ファイルを用意する．

```text
src/private/data/reviews/スキー場ID/detail.json
src/private/data/reviews/スキー場ID/article.json
```

ChatGPT で detail.json を作り，Codex や Claude Code で article.json を作る流れは変わらない．
その後，例えば次のように依頼できる．

> このスキー場の detail.json と article.json を検証し，本番との差分を確認する．問題がなければ本番へ反映すること．

担当 AI は下のコマンドで差分を確認し，反映を実行できる．キーを毎回チャットに貼る必要はない．
「記事を書いて」という依頼だけでは，本番公開まで指示したことにはならない．

### Mac の設定 (初回のみ)

プロジェクト直下の `.env.local` に，既存の API キーを設定する．

```dotenv
API_BASE_URL="https://実際の本番ドメイン/rusutsu"
API_BEARER_TOKEN="GitHub Secretsに登録したキー"
```

専用コマンドは API へ直接通信するため，ローカルの開発サーバーや DB を起動する必要はない．
依存ライブラリは通常のセットアップで準備する．

### コマンドを自分で実行する場合

最初は差分を確認する．`rusutsu-resort` は実際の対象 ID に置き換える．

```bash
mise run reviews:publish -- --resort rusutsu-resort
```

ここでは保存しない．2 ファイルの検証と，本番の現在値との比較を行う．
確認内容は `.review-publication-plan.json` に保存される．このファイルには API キーを含めず，Git にも登録しない．

内容がよければ，同じコマンドに `--apply` を追加する．

```bash
mise run reviews:publish -- --resort rusutsu-resort --apply
```

プレビュー後に JSON や接続先が変わっていたら停止する．本番が他の人に更新されていても停止する．
その場合は，本番の変更を取り込んで JSON を見直し，最初の差分確認からやり直す．
成功すると 2 ファイルが一緒に保存される．片方だけの反映にはならない．

複数のスキー場を並行作業する場合は，`--plan /tmp/スキー場ID-review-plan.json` など別々の保存先を指定し，
反映時にも同じ `--plan` を指定する．プランは非公開の作業ファイルとして扱う．

## 手動で行いたいとき：管理画面で 2 ファイルを選ぶ

1. 本番の `/rusutsu/admin/review` を開き，「作成したJSONを取り込む」を押す．
2. 同じスキー場の `detail.json` と `article.json` を，2 つまとめて選ぶ．
3. 対象 ID と，それぞれの「現在の内容」「保存する内容」を確認する．
4. 「確認した2ファイルを保存する」を押す．
5. レビュー編集画面へ戻り，公開画面も再読み込みして内容を確認する．

新規レビューにも対応する．スキー場自体はマスターに登録されている必要がある．

従来の good/bad 形式と，AI 制作で使う reason/full の箇条書き形式に対応する．JSON の形式や調査の証拠を勝手に書き換えて保存することはない．
箇条書き形式のレビューは，一覧の「AIで作成した形式のレビュー」から現在の JSON を確認し，更新した 2 ファイルを取り込める．
文章の事実確認や文体のチェックは制作時のスキルで行う．公開処理は形式・対象 ID・更新競合などを検証する．

既存 JSON の確認では，`naeba` に形式の不一致，`osorakan-snow-park` と `rusutsu-resort` にフォルダー名と JSON 内の対象 ID の不一致が見つかっている．
これらは自動修正せず，対象のスキー場と内容を確認してから反映する．
各ファイルは 2 MiB 以内である．本番 API に接続したローカル管理画面でも使える．
管理画面の場合は Google ログインを使うため，ブラウザーに API キーを入力する必要はない．

## JSON と Git はどう使い分けるか

| 場所 | 役割 |
| --- | --- |
| Mac の JSON | AI による調査・記事作成・内容確認の作業場所 |
| rusutsu-library | 調査資料と制作履歴の保管．push だけで本番 DB は更新しない |
| 本番 DB | 公開中の内容．管理画面または反映コマンドで更新 |

サーバーで直接編集した内容が Mac の JSON へ自動で戻るわけでもない．
古い JSON を反映する前には必ず差分を確認し，残すべき本番の変更を取り込む．

今回の取り込み画面と反映コマンドはレビュー専用である．リフト券料金の JSON 取り込みには使わない．
リフト券料金は既存の管理画面で編集・保存できるが，外部で作成した新しい料金 JSON を一括で取り込む導線は別途対応が必要である．

`private/data` 全体は削除できない．名寄せ辞書・気象関連の辞書・過去の取得結果・初回移行用データなど，
他にも使用中のファイルがある．今回の旧称・ふりがなの DB 化は，全ファイルの削除を可能にする変更ではない．
