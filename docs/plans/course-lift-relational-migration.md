# コース・リフトの個別レコード化：実装と移行手順

2026-09-25。管理画面、個別行テーブル、移行CLIを実装。検証用DBで全件移行を確認。本番マイグレーション・デプロイは未実行。以下の「実装済みの範囲」が現在の状態で、その後の調査記録は設計時点の記録。

## 実装済みの範囲

- 管理画面に「コースのまとめ方」を独立した編集ステップとして追加。線編集と詳細編集の間で、地図と一覧を見ながら「連続区間／同じコースの別ルート／同名の別コース」を確定する。モーダルではない。
- 始点・終点の10m以内の接続から順序を提案。逆向き座標も検出し、標高があれば下り方向を提案する。標高なしは順序を確認する。分岐・ループ・離れた線は連続と自動確定しない。座標自体は反転・結合しない。
- 区間は1からの番号。詳細画面では必ず各線を別行で表示し、難易度、詳細、営業情報の対応を個別編集する。名前・形状が変わればまとめ方の再確認が必要。
- `MapCourse` / 任意の `MapCourseGroup` / `MapLift`。固定ID、所属、区間順序、主要属性、元Feature全体、元形状、派生Featureを同一レコードに保持する。旧SurfSnow Course/Liftには触れない。
- 新規編集では名前の `_#` や `無名_N` 自動命名を使わない。旧 `_#上部・下部・N部` は明示的なグループに変換し、旧名称は原文のまま保持する。普通の `_上部` と `_2` は独立。対応表は固定ID参照を追加し、同名・改名後も別々の対応／対応なしを保持する。
- 移行マーカー有効後は、既存DataDocument保存と個別行の同期を同じDBトランザクションで行う。削除された個別行は物理削除せずarchivedAtを設定する。公開・adminへの互換GeoJSONを残し、読取時に元Featureと個別行を照合する。JSON原文を廃止する最終段階ではなく、互換性を維持した段階的移行。
- コース・リフトと対応表は同一保存バッチに含め、競合時に片方だけ保存されないようにした。形状未変更ならZ値・未知のFeatureメンバーを保持する。未編集の詳細生値（数値文字列、未対応難易度など）も維持する。
- 固定IDによる内部API: `/api/internal/v1/map-entities?kind=course&id=...`（admin-data認証）。

## 移行の実行手順

1. 対象書込を一時停止して、最新DBスナップショットとGeoJSONバックアップを取得する。2026-09-25のGitバックアップはその時点のデータであり、適用直前のバックアップの代用にしない。
2. 対象リリースのPrisma migrationを確認して適用する。今回のSQLは `prisma/migrations/20260925120000_add_map_entities/migration.sql` で、新規テーブル追加のみ。既存テーブル・文書は変更しない。別作業の未適用migrationも含まれる可能性があるため、適用対象を確認する。`migrate reset` は使わない。
3. 正しい対象DBへのDATABASE_URLで `mise run db:migrate-map-entities -- --dry-run --report src/private/data/resorts-temporary/tmp/map-entities-migration/live-report.json` を実行する。
4. レポートの件数、issues、inputHash、ID対応を確認する。CLIは既定dry-run。オフライン確認は `--from-backup src/private/data/backups/course-lift/2026-09-25/manifest.json` を指定できるが、バックアップ内容が現在のlibraryファイルのhashと一致する必要がある。
5. 同じDBへ `mise run db:migrate-map-entities -- --apply --expected-hash <確認したinputHash> --report src/private/data/resorts-temporary/tmp/map-entities-migration/apply-report.json` を実行する。最新文書のhashが変わっていれば中止する。適用レポートの `committed: true` を確認する。
6. 元文書を `map_document_backups` に保存した上で全件を同一トランザクションで移行・照合する。成功時だけ `map-entities-v1` マーカーを有効にする。失敗は全体ロールバック。再実行はID・件数を増やさない。
7. 安比の5区間、通常の `_`、同名別ルート、リフト中間駅、対応表、admin保存・公開画面を対象環境でも確認して書込を再開する。旧JSONとバックアップは消さない。

接続先は `src/lib/prisma.ts` のDATABASE_URL設定を使う。CLIは本番API経由の実行ではない。本番適用はこの作業では実施していない。

## 名前記法の意味を保持する

ユーザーの仕様を正とする。

| 元の名前 | 移行後の扱い |
|---|---|
| 白樺_#上部 / 白樺_#下部 | 別々のCourse行。同じCourseGroupに所属し、区間番号は1／2 |
| 白樺_上部 / 白樺_下部 | 独立したCourse。名前の類似だけでグループ化しない |
| オオタカ_#1部〜_#5部 | 5行を1グループへ。ラベルと数値の区間順序を保存 |
| カッコウ_2 / カッコウ_3 | 独立したレコードとして保持。番号だけから結合・削除・同一視しない |
| 正式名称に含まれる第2等 | 名称をそのまま保持 |

既存実装では `resortMapMerge.adjustCourseName` が `_上部` を `上部` に変換し、`_#上部` は残す。その後 `parseFinalizedCourseName` が上部／中部／下部をグループ化する。後者の正規表現だけを見ると `#` は省略可能だが、通常の表示経路では前段の変換により区別されている。

既存関数を組み合わせた読み取り検証で、`白樺_#上部` はグループ化対象、`白樺_上部` は独立、`オオタカ_#1部` と `_#5部` は現状グループ化されないことを確認。移行後は記号解析に依存せず明示的なgroupIdで扱う。現状の未対応を仕様として固定せず、意図した改善として差分をレビューする。

安比高原の本番原文では「セカンド第1」「オオタカ」はどちらも1〜5部。オオタカの配列順は5・3・4・1・2なので、既存の表示順と区間の意味上の順序は別フィールドにする。カッコウやキツツキには番号だけの別線もあるため、ベース名による一括統合は禁止。

グループ化は表示上の関連付けであり、座標の連結ではない。途切れた線を直線で結ぶ処理は入れない。全体の標高プロファイルが必要なら接続・方向・並びの検証を別途行う。

## 推奨する最小構成

- Course: 1本の採用線と、独立した難易度・クローラー対応を持つ単位。
- CourseGroup: まとめて表示・選択したいCourseだけが所属する任意のグループ。
- Lift: 1リフトの属性と採用線。今回の要件ではグループ表を追加しない。
- 営業情報の対応表: 名前ではなく固定Course/Lift IDを参照。既存対応表の意味と未対応指定を保持する。

Courseには固定ID、所属スキー場、元名称、表示名、groupId(nullable)、sectionLabel(nullable)、sectionOrder(nullable)、displayOrder、各属性、元形状JSON、派生形状JSON(nullable)、出典・確認状態・更新versionを持たせる。CourseGroupには固定ID、所属、表示名・表示順を持たせる。グループと子の所属一致はDB制約等で担保する。非グループコースは1行で完結する。

CourseGeometryの独立テーブルは作らない。ただし現状の編集用beforeと標高補完済み10m/20mは両方必要。1つの採用線の元データと派生データとして同じ行で保持し、geometryRevisionと派生元revisionを関連付ける。バックグラウンド補完は古いrevisionの結果で新しい形状を上書きしない。

既存のSurfSnow由来Course/Liftは移行元にしない。新しい物理テーブル名で作成し、旧モデルとの名前衝突を避ける。古いテーブルの整理は別作業。IDは名前・配列順・スキー場所属の変更で変えない。

adminには任意のグループ選択・区間ラベル・区間順序を追加する案。名前に `_#` を入力しなくても設定できる。既存の項目・所属変更・競合検知・クローラー割当・下書き保護を維持する。グループ選択は全所属線、線選択は単一Courseを対象にする。

## グループと営業情報・統計を混同しない

グループ所属は表示の関係。営業情報は各Courseに対応付ける。複数Courseが同じ取得項目を参照でき、同じグループ内で異なる取得項目を使える。未対応を名前の自動推測で埋めない。

安比高原ではセカンド第1の各部に距離2500m、オオタカの各部に3000mが繰り返し入っている。これを合計しない。公式の全体距離か区間距離かは要確認として原値を保持。形状計算距離と公式値を分離し、難易度の混在・不明区間・一部営業を集約表示で明示する。

## データを残して切り替える手順

1. 追加のみのスキーマ変更を設計する。旧DataDocumentと旧Course/Liftは削除・上書きしない。今回のバックアップとは別に、本番移行直前のDB全体バックアップを既存VPS内手順で取得する。
2. 今回のコミットとmanifestを使い、隔離した検証DBで復元する。元の全文書をhash照合してから新テーブルへ変換する。
3. 移行台帳を作る。各元文書・配列位置から固定IDへの対応、beforeと派生線・詳細の対応、公開採用／未確認OSM／保留、未対応項目を記録する。名前だけで同一視しない。派生側にしかない線、詳細だけの行、未登録・統合前のスキー場IDも隔離・保持し、消さない。
4. 冪等なバックフィルを試す。再実行でID・件数が増減しないことを確認する。元形状と10m/20mを別コースとして二重登録せず、曖昧な対応は保留にする。OSMと手動整備の採用優先度は現在のローダーと照合する。
5. 全レコードを機械照合する。単純な表示件数に加え、元Feature全件の行き先、未知属性・元値、座標精度・Z値、属性の対応、クローラー対応、並び、所属、グループ非所属、復元可能性を検証する。beforeの1909件と派生の1853件の差などは原因と行き先を全件説明する。
6. 読取切替フラグを用意し、旧・新の出力を並行比較する。現行APIのGeoJSON形式への変換層を挟み、画面を急に全面変更しない。安比5分割、`_#上部`、`_上部`、`_2`、同名コース、難易度混在、異なる取得項目、標高欠損、中間駅、所属移動を回帰確認する。
7. 本番切替時はコース・リフトadminの保存、関係するAPI書込・インポート・所属統合、標高補完ジョブなど対象文書の全書込経路を短時間停止し、最終スナップショットとの差分を反映する。新テーブルを読取検証してから書込先を切り替える。ブラウザの古い下書きは退避・バージョン判定して上書きを拒否する。
8. 切替後のロールバックを成立させる。猶予期間は新テーブルを正本とし、旧形式を同一トランザクションで互換出力する。両方を独立に編集可能にしない。互換出力で表現できない新機能は猶予期間中無効にする。新規編集後も旧経路へ戻せることを検証する。
9. 安定確認・復元リハーサル後に旧読込経路を廃止する。DataDocument原文・移行台帳・バックアップの保持期間を別途決め、移行と同時に削除しない。

本番の切替条件は「説明不能な欠落0件、未解決の対応衝突0件、保持対象の全値照合、admin保存往復・既存表示の回帰確認、復元リハーサル成功」。解消できないレコードがある場合は旧経路を維持し、消して成功扱いにはしない。

## 追加調査：無名記法と対応作業一覧

2026-09-25の実装前調査記録。現在の状態は冒頭の実装済み範囲を参照。

### 現在の「無名」はまだ動作条件に使われている

- 対応表が設定済みの場合、名前によらず `geojsonName` の行と `crawledName: null` で「対応させない」を表現できる。`reconcileSavedRows` はこの指定を維持する。したがって「対応不要」の目的で `無名_連絡` と命名する必要はない。
- 対応表未設定の旧フォールバックでは、`canonicalBase(name) === "無名"` のとき対応なし警告を抑制している。対応表がないスキー場まで名前だけ削ると挙動が変わる。
- `createSuggestedRows` は `無名` / `無名_...` を自動対応候補から除外する。`compactMappingRows` にも無名とクローラーの組を切り離す処理がある。ただし通常の保存済み行の再照合は `reconcileSavedRows` がそのまま保持するため、「保存された無名の対応は必ず解除される」とは言えない。
- adminの無名操作は空名と `unnamed` を扱い、保存前に `無名_1` 等を自動採番する。対応付けUIは `unnamed` / 空名の項目を対応させる際にクロール名へ改名する。
- 表示名変換は `無名_連絡` を `連絡`、`無名_1` を `無名` にする。地図ラベルは無名で始まる文字列を非表示にする。

結論: 対応不要を名前に埋め込む設計は廃止できるが、現時点で特殊扱いがすべて消えているわけではない。

### 移行後は別の情報にする

| 情報 | 表現案 |
|---|---|
| 名前 | 例: 連絡。内部識別は固定IDに任せる |
| 名前が判明していない | nameの欠損または名称状態として表現。対応不要と混同しない |
| 営業情報の対応 | mapped / intentionally_unmapped / pending の明示状態と対応先 |
| 地図ラベルを表示するか | 表示ポリシーとして扱う。名前の接頭辞で決めない |
| 同じコースとしてまとめるか | groupId |
| 区間名と順番 | sectionLabelとsectionOrder |

画面文言は「対応済み」「対応させない」「未確認」など。対応済みなのに取得先から項目が消えた場合は、保存した対応を維持して欠損を別途表示する。「対応させない」を取得失敗や未調査と同一視しない。

既存の `crawledName: null` は現行の明示指定として保持する。ただし自動提案由来か人が判断したかの履歴は現在の文書だけでは判別できないため、移行時に「公式に情報がないことを確認済み」といった意味を勝手に追加しない。

### 対応チェックリスト

| 対象 | 必要な変更・検証 |
|---|---|
| DB / 読書API | Course・任意CourseGroup・Lift、固定ID、属性と形状、revision、未知属性の保持。旧SurfSnow表は流用しない |
| コースadmin | グループ指定／解除、区間ラベル・順序を追加。`_#` の手入力と自動命名を置き換える。既存の全入力欄と所属移動を維持 |
| 分割・結合操作 | 分割後のID、属性、営業対応の引継ぎを明示。表示グループ化と物理的な線の結合を別操作にする。異なる属性・対応を持つ線の結合は黙って片方を採用しない |
| リフトadmin | 固定IDで保存。全属性、中間駅と生座標、所属変更、確認状態を維持 |
| クローラー対応UI / 保存 | geojsonName参照をID参照へ。改名で対応が切れない。同名の別線を扱える。対応済み／対応させない／未確認を区別 |
| 自動対応候補 | 無名接頭辞・位置順での自動確定を廃止し、名前の類似は提案用途に限定。人の指定を保持。取得元側の名前照合は残るので取得元変更は要検知 |
| 無名操作 | 「名前不明」の意味だけを持たせる。`無名_N` 採番と対応不要・非表示の連動を解除。対応付け時の自動改名も見直す |
| 公開画面 / 地図 | 名前解析によるgroupId生成・ラベル整形を廃止。固定IDで選択、ハイライト、詳細、ラベル配置、プロファイルを扱う |
| 営業状況と集計 | グループを明示的に集約。5分割・混在難易度・一部営業・不明状態・全体距離の重複を扱う |
| 詳細・画像・検索ワードの突合 | canonicalBase・接尾辞除去による名寄せをIDや明示的な関連へ移す。複数区間の画像共有チェックもgroupIdに合わせる |
| 標高補完 / 派生形状 | 元形状と派生形状を固定ID・revisionで対応。古いジョブ結果による上書きを拒否 |
| インポート / エクスポート | GeoJSONに安定ID・groupId・ラベル・順序等を出す。旧形式は入口で解釈し、曖昧なものを自動統合しない。往復で未知属性も保持 |
| スキー場統合・割当変更 | 固定IDとグループ所属を維持。移動元・先の更新を同一トランザクションで扱う。同名による別コース消失を防ぐ |
| ブラウザ下書き・キャッシュ | 形式versionを更新。古い下書きの退避・変換・競合確認。公開データのキャッシュも更新 |
| チュートリアル / ヘルプ / テスト | `_#`・`無名_N` の説明を新UIへ。旧入力互換と新しい明示設定の両方を検証 |
| バックフィル / 切替 | 生の旧名称・原文を保持して対応台帳を作り、名称変更はID関連付け完了後。復元・全件照合・ロールバックを先に検証 |

移行は「安定IDと明示関係の追加 → 全件対応付け → admin/API/表示を切替 → 旧命名への依存除去」の順にする。先に既存JSONの名前だけを一括変更しない。
