# 編集者と承認フロー

## 第1段階：アクセス権限

Google認証後の権限に `editor`（編集者）を追加した。画面と Server Action は、JWTに残った古い権限ではなく、DBの現在の権限を確認する。

| 操作 | 閲覧者 | 編集者 | 管理者 |
| --- | --- | --- | --- |
| 公開情報の閲覧 | 可 | 可 | 可 |
| 6種類の編集ツール | 不可 | 可 | 可 |
| 編集結果の直接反映 | 不可 | 不可 | 可 |
| 自分の申請の確認・取り下げ | 不可 | 可 | 管理者として確認 |
| 全員の申請の確認・修正・承認・却下 | 不可 | 不可 | 可 |
| ユーザー一覧・メールアドレス・権限変更 | 不可 | 不可 | 可 |
| クローラー画面・実行・診断 | 不可 | 不可 | 可 |
| 確認済みフラグ・標高の再取得・スキー場統合 | 不可 | 不可 | 可 |

編集者のダッシュボードではユーザー一覧を取得しない。申請の取得条件にも本人のIDを指定し、他人の申請や管理者の修正案を編集者へ返さない。クローラー関連ページも管理者を確認する。

## 第2段階：申請の保存

編集者の保存操作は、スキー場情報・リンク・リフト・コース・リフト券・レビューのすべてで申請になる。コースの並び順、営業情報の対応表、レビューJSONのアップロードも対象。

既存の検証・変換処理を使って反映予定のデータを準備し、公開DBへの書き込みと標高の取得は行わない。リフト・コースと関連リンクは同じ申請にまとめる。

保存するものは、提出時の入力、変更前のデータと版、反映予定のデータ、管理者が修正する候補、申請状態、操作履歴。提出時の入力は、管理者による修正後も保存する。

申請状態は「承認待ち」「反映済み」「却下」「取り下げ」「競合」。1人の承認待ち申請は最大100件。入力の大きさ・構造・対象IDをサーバーで検証する。

## 第3段階：管理者の修正と承認

管理者は申請詳細で変更前との差分とリフト・コースの地図を確認し、項目をその場で修正できる。「修正内容を検証・保存」では公開情報は変わらない。保存した修正案を確認後、「承認して反映」で公開する。

対象のスキー場IDや編集元の版は変更できない。修正画面は既存項目の変更に対応し、項目・行の追加や削除を伴う作り直しは編集ツールから改めて申請する。

承認時には、管理者と申請者の現在の権限、申請の状態と版、変更前データのハッシュ・版・更新日時を再確認する。古い申請で新しい公開情報を上書きしない。公開データ、申請の「反映済み」、操作履歴、標高更新ジョブを同じDBトランザクションで確定する。

同時承認、承認と取り下げの競合では、1つの操作だけが成立する。途中のDB処理が失敗すると全体を取り消す。公開データの競合時は「競合」となり、最新データからの再申請が必要。

編集者は管理者が修正した内容の再承認を求められず、「反映済み」で完了する。却下には理由が必須。

## 第4段階：標高更新と運用

標高の外部取得は承認後に行う。ジョブをDBに保存し、起動時と毎分に実行する。複数サーバー間の同時実行をPostgreSQLのロックで防止し、最大5回試行する。対象データが後から変わっていれば古いジョブを破棄する。

`DISABLE_EDIT_REQUEST_JOBS=true` で標高ジョブの実行を停止できる。Google認証の設定自体は変更していない。

## 導入条件と未実施の作業

新しいテーブルとユーザー権限のCHECK制約は `prisma/migrations/20261002000000_editor_requests/migration.sql` にある。本番へのマイグレーション適用・デプロイは今回のローカル実装には含めていない。

申請と公開データを1つのDBで確定するため、DB処理は公開データを保持するサーバーで行う。`DATA_API_BASE_URL` が設定されたlocalhost環境でも、申請用の内部APIを通して一覧・内容の取得、編集の申請、修正案の保存、承認・却下・取り下げができる。ローカルDBへ申請を保存することはない。

### localhostからサーバーのDBを使う仕組み

`src/server/edit-requests/remoteClient.ts` が `POST /api/internal/v1/edit-requests` を呼ぶ。既存の内部APIと同じ `admin-data` 用トークンを使い、トークンはブラウザーへ渡さない。現在の `.env.local` の `DATA_API_BASE_URL` を維持して利用する。

ローカルのログイン済みユーザーに紐づくGoogleアカウントの識別子を、ローカルサーバーで取得して送る。画面が指定したユーザーIDや権限は採用しない。接続先サーバーでは、Googleアカウントからサーバー側のユーザーを検索し、現在のDB権限を再確認する。ローカルとサーバーでユーザーIDが違っても対応できる。

ローカル側の操作権限の確認に加え、接続先サーバーにも同じGoogleアカウントが登録済みで、編集者または管理者の権限が必要。管理者の修正・承認には両方の環境で管理者権限が必要になる。未登録のアカウントを内部APIが自動で作成・昇格することはない。

承認のDBトランザクションと標高ジョブの登録・実行は接続先サーバー上で行う。localhost側で承認ボタンを押しても、ローカルDBとサーバーDBに分けた更新は行わない。

この内部APIをサーバー側にも配備する必要がある。接続先が未対応の場合は、申請一覧にサーバーの更新が必要だと表示する。旧APIや管理者向けの直接書き込みAPIへ自動で切り替えることはない。

導入時は、未知のユーザー権限がないこと、公開データがDBへ移行済みであることを確認し、既存データを保持したままマイグレーションを適用する。その後、管理者が必要なユーザーを編集者へ変更する。

## 検証

専用の使い捨てPostgreSQLで、実際のServer Actionと保存処理を用いて検証した。認証済みIDとNext.jsの応答フックのみを検証用に置き換え、権限は実際のDBから取得する。

権限の変更、他人の申請へのアクセス、管理者による修正、全編集種別、同時承認、取り下げとの競合、公開データの競合、DB途中失敗時の取り消しを検証する。Googleの実アカウントを使ったOAuth往復と本番接続は別途の導入確認となる。

統合テストは `src/server/edit-requests/workflow.integration.test.ts`。実行は明示した検証DBだけを受け付け、本番の `DATABASE_URL` は使用しない。

- 通常のテスト：最新の実行で1,029件成功、統合テストの未指定時スキップ1件。Playwrightを含め、ブラウザー起動可能な環境で実行した。
- 使い捨てDBの統合検証：15項目成功。営業情報の対応表と、DBへの地図関連テーブルの反映も確認。
- 申請の準備・権限・入力検証の単体テスト：6件成功。
- Playwright：編集者のダッシュボード、リンク編集からの申請、管理者による修正と承認、編集者の反映済み表示、クローラーと閲覧者のアクセス拒否を確認。390px幅の表示とブラウザーの実行時エラーも確認。
- 初回の型チェックでは別作業の一時スクリプトに5件のエラーがあった。現在の設定では一時作業ディレクトリが除外され、通常の `mise run typecheck` が成功している。
- Biomeと差分の空白チェック成功。Webpackの本番ビルド成功。通常のTurbopackビルドは実行環境の外部フォント接続・子プロセスのポート制限で失敗した。

画面検証は検証用秘密鍵で署名したAuth.jsセッションと検証DBを使用した。実際のGoogleアカウントでのOAuth往復や、本番でのマイグレーション・運用確認は実施していない。

localhost経由の追加検証では、2つの独立したDBと実際のHTTP APIを使用した。Googleアカウントが同じでユーザーIDが異なる場合の対応、申請がサーバーDBだけに保存されること、管理者が修正した内容の承認、ローカルDBが変更されないこと、他人の申請の拒否、サーバー側の降格、無効なトークン・異なる用途のトークン・権限偽装の拒否を確認した。

接続先の新APIの配備確認は、認証情報を送らずHTTPステータスだけを取得した。2026-10-02時点では404で未配備。サーバーへの配備は行っていないため、実際のサーバーDBを使うlocalhostでの操作には、このコードのサーバー反映が必要。
