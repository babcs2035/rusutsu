# ユーザー投稿機能

2026-10-31 時点の実装と運用手順。既存の編集者向け申請とは入口を分け、匿名の情報修正には `EditRequest.kind = public-correction` を使う。公開投稿は1回の現地訪問を表す親 `CommunityPost` と、内容別の子 `CommunityEntry` に保存する。

## 画面と保存先

| 機能 | 入口・実装 | 保存・審査 |
| --- | --- | --- |
| 匿名の修正提案 | 詳細の「情報を修正する」、`/corrections/[resortId]` | `EditRequest` / `EditRequestEvent`。承認前は正式データを変更しない |
| 基本情報・関連URL | 基本情報、`/corrections/[resortId]/links` | スキー場マスターまたは既存 `SkiResortLinks.json` 文書への項目単位CAS |
| コース・リフト情報、一括修正 | 修正トップから対象・項目を選択 | 変更なしの行を含めて送信し、審査時に変更なしと区別 |
| 位置・追加・削除、属性の区間設定 | 修正内の地図 | 元座標を保存。スナップ・線の統合なし。属性区間は0〜1の距離比率で別々に保存 |
| 料金・出典の報告 | 計算結果・価格セル・出典表記の操作 | 条件・結果・識別子を非公開添付。管理者が確認して元データを修正 |
| 管理者による調整・部分承認 | `/admin/corrections` | 提出内容・候補・実際の反映を分離。元データと申請版が変わっていれば拒否 |
| 現地レポートと項目 | `/community/[resortId]`、詳細の「投稿」タブ、地図の「＋投稿」 | Googleログインと公開名設定後、投稿APIへ送信。公開状態で作成し、非同期モデレーションへ登録 |
| レポート項目 | 1回の投稿でCOURSE・LIFT・MOGUL・ITEMのどれか1項目 | 子 `CommunityEntry` に1行だけ保存（`position` は0のみ）。編集は同じ行を書き換える |
| コメント・いいね・通報・通知 | 投稿詳細、ホームのアカウント | 投稿者の認可・版を検証。匿名通報可。通知はサイト内のみ |
| 公開名・履歴・削除 | `/profile/[id]`、`/account/community` | Google名・ニックネーム・匿名。メールと選択していない本名を公開しない |
| AI・管理者対応 | `/admin/community` | 永続キューで事後判定。古い版の判定は新しい編集に適用しない。停止は管理者だけ |

日付・時刻は親 `CommunityPost`（`observedOn`／`observedTime`）、項目の内容は子 `CommunityEntry` に保存する。項目種別はCOURSE（コース）、LIFT（リフト）、MOGUL（コブ）、ITEM（パーク）。写真は任意。滑走日時とコース・リフトの対象・状況は必須で、コブは場所、パークは場所とアイテムの種類も必須。コース・リフトの場所は任意で、地図から消去できる。投稿地点はスキー場のコースまたはリフト線から500m以内であることを画面とサーバーで確認する。どちらの線データもない場合は地点を検証できないため、地点付き投稿を受け付けない。必須欄を満たせば投稿でき、写真や自由記述は任意。コース・リフトには、クローラーの営業状況とは別に現地で見た「状況」（`status`。コースはオープン・積雪不足・クローズ、リフトはオープン・減速中・クローズ）が必須。緑のチェック・黄色の三角の注意マーク・赤の進入禁止マークで示す。リフトの速度は「速い・普通・遅い」（`liftSpeedLevel`）とm/sの数値（`liftSpeed`）の両方を任意で持てる。コブの深さは `depth`。以前の複数項目レポートにあった全体の感想・全体評価・項目評価・コース状態・コブ／パークの有無（`present`）は、投稿がない段階で列ごと削除した。一覧の平均★表示もない。いいね、コメント、通知、AI判定、非表示、削除はレポート全体を単位とする。

公開地図では下部パネルの上に「営業中のみ」「投稿」「＋投稿」と地図の出典を独立した1行で配置する。「投稿」は、公開状態かつ地図に表示できる投稿があると取得で確認できた場合だけ有効にする。0件・未取得・取得失敗時は半透明にしてチェックできなくし、取得失敗時は再試行できる。地図にはコース・リフト・コブ・パークの4種類を初期状態ですべて表示し、表示項目のボタンで複数選択する。「すべて」ボタンは置かない。滑走日を基準に、初期期間は「過去1週間」→「今シーズン」→「全期間」の順で投稿がある範囲を選ぶ。手動で期間を変更した後は、0件でも自動変更しない。投稿ON中のパネルは「滑走日・期間・件数・設定」「表示項目・4種類のボタン」とし、難易度／斜度・背景の切り替えは設定内に残す。コースは青、リフトは青緑、コブは紫、パークは橙で、種類ボタン・写真の枠・地点の色を統一する。写真ありは代表写真と残り枚数、写真なしは点で表示する。地点のないコース・リフト投稿は対象線上の代表位置に対象名付きの札を表示し、撮影地点とは区別する。同じ対象や近接した投稿は件数付きでまとめ、ズームで再配置する。押すと地図上で投稿を確認し、コース・リフト全体を強調でき、写真は既存の拡大表示を使う。地図の有無・一覧は軽量GETで取得し、小さい地図と拡大地図で取得結果・期間・種類の選択を共有する。後続ページを待たずに最初のページから表示し、写真は表示範囲内のマーク分を取得する。スマホのスキー場詳細の小さい地図にも同じ「営業中のみ」「投稿」「＋投稿」と出典を1行で置き、幅が足りないときは出典だけを1段上の右端へ回す。投稿中のスマホの地図には拡大・現在地・営業フィルターを出さない。スキー場詳細の「投稿」タブは、1段目に表示期間（全期間・今シーズン・過去1週間・過去3日）・表示する項目（すべて・コース・リフト）・並び順・青い「＋投稿」、2段目に滑走日の開始〜終了を置く。表示期間を選ぶとその期間の日付（全期間は空）が入り、日付を手で変えて当てはまる期間がなければ「期間指定」と表示する。「今シーズン」は9月末で区切り、10月1日から今日までの滑走日を対象にする（地図の投稿表示も同じ）。投稿を押すと、詳細のコース選択とは別に、その投稿のコース・リフトを地図で強調し、場所があれば印を出す（もう一度押すと解除）。投稿を押すたびに、保存済みの表示範囲や同じ対象の選び直しに関係なく、その対象へ地図を寄せる。コース・リフトがない投稿や、投稿のコースが今の地図データにないときは場所へ寄せる。スマホの投稿タブには地図をタブの下に貼り付けて出し、地図の操作ボタンは出さない。投稿カードは投稿者名を太字で大きく出し、右上に「滑走日時」、下にコメントといいねのアイコン（件数付き、高さ36pxの押しやすい範囲）と右端に「投稿日時」（日本時間）を並べる。320pxのスマホではボタンの間隔を詰めて1行に収める。「投稿の詳細」リンクは置かない。いいねは押した瞬間に表示を切り替え、失敗したら戻す。コメントのアイコンでその場にコメント一覧と入力欄を開く。いいね・コメントは押した時点でログインを確かめ、未ログインならGoogleログインへ進めて元の画面へ戻す（戻り先はサイト内の画面に限る）。写真を押すと、後ろが透ける薄い背景の真ん中に写真を浮かべて拡大表示し、×は写真の右上に置く。動きは付けず、読み込み前から縦横比で大きさを決め、読み込み済みの小さい写真を敷いて表示が広がらないようにする。スマホは画面全体、PCは詳細パネルの範囲に重ねる。一覧・写真一覧・投稿フォームの小さな写真は `?size=thumb`（320px）で受け取り、元の写真（最大2048px）は拡大表示だけで読み込む。地図のマークは `?size=map`（160px）を使う。新しい写真は保存時に320px／160pxの派生画像も生成する。既存写真は初回取得時に派生画像を生成・保存し、その後は小さい画像だけを配信する。派生画像も毎回公開状態・権限を確認し、`no-store` で返す。投稿フォームのコース・リフトは、スキー場詳細で読み込み済みの地図データから作り、開くときに取り直さない。ログインしているかはブラウザが持つログイン状態で判定し、未ログインなら投稿画面の中に「現地レポートを投稿するにはログインが必要です」と「Googleでログイン」を出す（サーバーへの問い合わせはしない）。ログインは別ウィンドウ（スマホでは新しいタブ）で行い、終わったら閉じて元の画面はログイン状態だけを読み直すので、地図や開いている画面を読み込み直さない。別ウィンドウを開けないとき、または元の画面がもう開いていないときは、投稿画面を開いた状態のスキー場詳細へ戻る。開発環境で未ログインのまま入力画面を確認するときは、ブラウザの localStorage に `rusutsu:composer-preview` = `1` を入れる（送信はできない）。サーバーでの照合も同じ地図を使い、連携エリアの子では詳細と同じく親の地図のコース・リフトを受け付ける。

## データ・写真

初期追加は `prisma/migrations/20261024000000_community_contributions/migration.sql`、日次レポートへの再設計は `prisma/migrations/20261025000000_daily_visit_reports/migration.sql`。公開前・未投稿の構造変更として、旧分割投稿の列を廃止し、子項目テーブルを追加する。旧形式の投稿データを取り込む移行処理は設けない。新規モデルは親レポート `CommunityPost`、子項目 `CommunityEntry`、`CommunityComment`, `CommunityLike`, `CommunityNotification`, `CommunityReport`, `CommunityModerationJob`, `ContributionPhoto`, `ContributionRateBucket`。`User` に公開名・選択方式・管理者による投稿停止日時、`EditRequest` に送信キーと写真関連を追加する。

投稿写真は必ず項目に付ける（`photos:<項目のclientKey>` だけを受け付け、項目に紐づかない写真はDB制約でも拒否する）。項目を消すと写真も消える。写真は1投稿で最大1枚、1枚8MiB以内。選び直した場合は、読み込みに成功した後で前の写真を差し替える。キャンセル・読み込み失敗では前の写真を残す。旧形式の複数写真は勝手に消さず、保存時には1枚に減らすか、写真を選び直す。2026-10-26の `20261026000000_report_entry_photos` マイグレーションで `ContributionPhoto` を項目へ関連付ける。ブラウザはアップロード前に写真のGPSと撮影日時を端末内で読み取る。場所は未指定かつ手動で指定・消去されていない場合、日時は手動変更されていない場合だけ写真情報から入れる。コース・リフトが未指定なら500m以内の最寄り線を候補にし、コブ・パークではその地点に近いコースを候補にする。2026-10-26の `20261026120000_single_item_reports` マイグレーション（投稿が1件もない前提。時刻列をNOT NULLで追加するため、投稿が残っていれば失敗して止まる）で、上記の旧列を削除し、時刻・リフト速度・コブの深さの列を追加し、コース・リフトにも位置を保存できるよう制約を変更する。保存前に画像を検証し、2048px以内のWebPへ変換してEXIF/GPS・元ファイル名を除去する。HEIC／HEIFはサーバー内の専用デコーダーで処理し、画像を外部サービスへ送らない。画像を `public` 配下や外部ストレージへ出さない。専用配信ルートが公開状態・管理者権限を確認し、`no-store` を返す。アカウント削除で写真実体・投稿・コメント・星・いいね・プロフィール等をDBの外部キーで削除する。匿名の修正依頼はアカウントと結び付けない。

投稿中はPC・スマホともスキー場のヘッダーを出さず、既存と同じ見た目の×だけを置く。最初のページで種類（コース・リフト・コブ・パーク）を選び、次のページで1項目を入力して投稿する。投稿後は「投稿ありがとうございます」と「別の投稿をする」を表示し、押すと種類の選択へ戻る。PCではスキー場詳細の右パネル、スマートフォンでは既存の地図を全高で保ち、その上に投稿パネルを重ねる。上端のハンドルをドラッグするかキーボードで高さを変えられ、地図インスタンスと表示範囲を保つ。地図でコース・リフトを押すと対象になり、種類の選択中なら押した種類の投稿を始める。場所は投稿種別にかかわらず地図の長押し（600ms、12pxを超えて動かない場合）で指定する。認識後は離したときのタップ選択を抑止し、パン・ズームを止める。長押し認識前の複数指操作や12pxを超える移動は、長押し指定を取り消す。コース・リフトの場所は「現在位置を取得」または地図の長押しでピンを置いて指定できる。長押しは地図をピン表示のまま保ち、近くのコース・リフトを投稿フォームへ自動補完する。自動補完した対象は地点の変更に合わせて更新するが、手動で選んだ対象は上書きしない。地図の線の選択や詳細パネルへの移動は起こさない。通常の地図タップは従来どおりコース・リフトを選択する。現在位置はボタン操作時だけ高精度で取得し、精度が100mを超えると確認を促す。日時も「現在時刻を取得」ボタンから日本時間で入れられる。種類の選択では「どの項目についてレポートしますか？」と添える。日時と、コース・リフトの状況は必須。各項目名の下に小さく「必須」「任意」を書き、数値の欄には薄く「任意」と表示する。「投稿する」は処理中を除いて押せ、必須項目が足りなければ各欄の下と送信ボタンの上に警告を出して最初の欄へスクロールする。リフトの速度はm/sとkm/hの欄を並べ、片方を入れるともう片方を小数第1位で換算して表示する。数値の欄は上下の矢印やホイールで値が変わらないよう、数字だけを受け付ける文字欄にする。×で閉じると下書きを保存して元の詳細へ戻る。ごみ箱からは確認後に下書きを破棄できる。入力はブラウザ内で自動保存する。テキスト等は `localStorage`、写真は `IndexedDB` に保存し、ユーザー・スキー場・新規投稿または編集対象ごとに分けて24時間で期限切れにする。入力変更時とページを隠す／離れるときに保存し、編集対象の版が変わっていれば古い下書きを復元しない。投稿成功時は下書きを削除する。写真を保存できないときは警告し、再選択を案内する。×で閉じるときに下書きを保存できなければ画面に留まり、再試行できる。ブラウザ／OSによる容量不足・データ消去、保存処理完了前の強制終了までは防げない。投稿URL `/community/[resortId]/new` はスキー場詳細内の投稿画面へリダイレクトする。動画・自然地形のジャンプスポット・体感難易度・当日の営業情報の手動変更は対象外。

開発環境では、投稿APIを利用できない場合や公開名が未設定の場合に、入力・確認画面だけのプレビューを表示できる。プレビューでは認証情報を偽装せず、投稿・更新などの書き込みを行わない。実際の投稿には本番OAuthでログインしたアカウントが必要。

`DATA_API_BASE_URL` が設定されている環境では、`features/community/actions.ts` は入力検証とAPI呼び出しを行うラッパーで、投稿の業務処理は `server/community/operations.ts` にある。書き込み・読み込みは `/api/internal/v1/community` へ送り、既存の `INTERNAL_DATA_API_ADMIN_TOKEN`（`admin-data` scope）で認証する。APIを呼べない場合にローカルDBへフォールバックしない。ローカルサイトのGoogle認証アダプターはローカルの `users` / `accounts` を使い、ローカル `community_*` テーブルは投稿データに使わない。投稿APIサーバーはGoogleの `providerAccountId` を本番の既存 `accounts` と照合し、対応する本番ユーザーIDで処理するため、投稿前に本番サイトでGoogleログインを完了しておく。リモートデータモードではローカルのコミュニティモデレーションスケジューラーを起動しない。

写真は入力欄の先頭で「写真を選択」から追加する。最初の有効な写真のEXIF撮影日時（DateTimeOriginal、なければDateTimeDigitized）を日時の初期値とし、同じ欄で変更できる。手動で変更した日時・場所（場所を消した場合も含む）や編集中の投稿の日時・場所は写真追加で上書きしない。地図やコース／リフトを明示的に選んでいた場合、その対象も写真GPSで置き換えない。撮影日情報がない写真ではアップロード日時やファイル更新日時から推測しない。GPSと撮影日は元の写真からブラウザ内で読み取る。現在位置・現在時刻も自動取得せず、各ボタンを押した場合だけ取得する。HEIC／HEIFはサーバー内の専用デコーダーでWebPへ変換してプレビュー・投稿に使う。写真を変換するために外部サービスへは送信しない。保存画像からは従来どおりEXIFを除去する。実際の端末・写真形式によってEXIFから読み取れる位置や撮影日時は異なるため、入力値を画面で確認する。

## 初期設定

1. 実際に保存する環境では、投稿APIを含むサーバーをデプロイし、投稿APIが接続する正本DBへコミュニティマイグレーションをすべて適用する。アプリ側の型生成が必要な場合は `mise run db:generate` を実行する。ここでは本番DBへの適用は実行していない。
2. Google OAuthは既存設定を再利用する。新しいプロバイダーは不要。Google認証設定は変更しない。リモート投稿では、ローカルの認証セッションに対応する `providerAccountId` が本番 `accounts` に存在する必要がある。
3. 本文の外部AIチェックを使う場合はサーバーの `OPENAI_API_KEY` を設定する。APIは [OpenAI Moderation](https://developers.openai.com/api/docs/guides/moderation) の `omni-moderation-latest` を使う。外部へ送るのは本文だけで、写真は送らない。
4. 写真もAI確認するには、**サイト内ネットワークで運用するAI判定サービス**を用意し、`COMMUNITY_MODERATION_URL`（例 `http://moderation:8080/v1/moderations`）を設定する。必要なら `COMMUNITY_MODERATION_TOKEN` と `COMMUNITY_MODERATION_MODEL` を設定する。URLはループバック・プライベートIPv4・コンテナ名に制限し、外部URLとリダイレクトを拒否する。
5. AIサービス未設定・失敗時も投稿は即時公開され、管理画面で未処理・失敗を確認できる。写真用サービスがない場合、本文の確認結果と写真の確認待ちを区別して残す。判定サービス自体のモデル運用はこのリポジトリには含めない。
6. `CONTRIBUTION_TRUST_PROXY=true` は信頼するプロキシが **常に X-Real-IP を上書きする構成だけ**で設定する。既定はfalse。通常の匿名送信には追加操作を求めず、短時間の連投だけブラウザ内の計算確認を行い、DB共有の頻度制限も適用する。
