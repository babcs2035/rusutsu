# ユーザー投稿機能

2026-10-26 時点の実装と運用手順。既存の編集者向け申請とは入口を分け、匿名の情報修正には `EditRequest.kind = public-correction` を使う。公開投稿は1回の現地訪問を表す親 `CommunityPost` と、内容別の子 `CommunityEntry` に保存する。

## 画面と保存先

| 機能 | 入口・実装 | 保存・審査 |
| --- | --- | --- |
| 匿名の修正提案 | 詳細の「情報を修正する」、`/corrections/[resortId]` | `EditRequest` / `EditRequestEvent`。承認前は正式データを変更しない |
| 基本情報・関連URL | 基本情報、`/corrections/[resortId]/links` | スキー場マスターまたは既存 `SkiResortLinks.json` 文書への項目単位CAS |
| コース・リフト情報、一括修正 | 修正トップから対象・項目を選択 | 変更なしの行を含めて送信し、審査時に変更なしと区別 |
| 位置・追加・削除、属性の区間設定 | 修正内の地図 | 元座標を保存。スナップ・線の統合なし。属性区間は0〜1の距離比率で別々に保存 |
| 料金・出典の報告 | 計算結果・価格セル・出典表記の操作 | 条件・結果・識別子を非公開添付。管理者が確認して元データを修正 |
| 管理者による調整・部分承認 | `/admin/corrections` | 提出内容・候補・実際の反映を分離。元データと申請版が変わっていれば拒否 |
| 現地レポートと項目 | `/community/[resortId]`、詳細の「投稿」タブ、地図の「＋投稿」 | Googleログインと公開名設定後、投稿APIへ送信。公開状態で作成し、非同期モデレーションへ登録 |
| レポート項目 | 1回の投稿でCOURSE・LIFT・MOGUL・ITEMのどれか1項目 | 子 `CommunityEntry` に1行だけ保存（`position` は0のみ）。編集は同じ行を書き換える |
| コメント・いいね・通報・通知 | 投稿詳細、ホームのアカウント | 投稿者の認可・版を検証。匿名通報可。通知はサイト内のみ |
| 公開名・履歴・削除 | `/profile/[id]`、`/account/community` | Google名・ニックネーム・匿名。メールと選択していない本名を公開しない |
| AI・管理者対応 | `/admin/community` | 永続キューで事後判定。古い版の判定は新しい編集に適用しない。停止は管理者だけ |

日付・時刻は親 `CommunityPost`（`observedOn`／`observedTime`）、項目の内容は子 `CommunityEntry` に保存する。項目種別はCOURSE（コース）、LIFT（リフト）、MOGUL（コブ）、ITEM（パーク）。全項目に写真・日時・場所の欄を置き、写真のEXIFから撮影日時・位置を入れる。コース・リフトは対象が必須、コブは場所、パークは場所とアイテムの種類が必須。コース・リフトは必須欄のほかに写真・雪質・混雑・待ち時間・速度・自由記述のどれか1つがあれば投稿できる。コース・リフトには、クローラーの営業状況とは別に現地で見た「状況」（`status`。コースはオープン・積雪不足・クローズ、リフトはオープン・減速中・クローズ）を任意で持てる。緑のチェック・黄色の三角の注意マーク・赤の進入禁止マークで示す。リフトの速度は「速い・普通・遅い」（`liftSpeedLevel`）とm/sの数値（`liftSpeed`）の両方を任意で持てる。コブの深さは `depth`。コース・リフトの場所は任意で緯度経度に保存する。以前の複数項目レポートにあった全体の感想・全体評価・項目評価・コース状態・コブ／パークの有無（`present`）は、投稿がない段階で列ごと削除した。一覧の平均★表示もない。いいね、コメント、通知、AI判定、非表示、削除はレポート全体を単位とする。

公開地図では下部パネルの上に「営業中のみ」「投稿」「＋投稿」と地図の出典を独立した1行で配置する。投稿レイヤーには子項目（コブ・パーク設備）の位置を表示し、選択すると親レポートの詳細へ移動する。パネル内は上段が凡例・フィルター、下段が難易度／斜度・背景・設定。営業中のみONではコース凡例を○・△・不明の選択へ置き換え、投稿ONでは投稿期間・種類を優先する。狭い幅では投稿フィルター表示中のリフト凡例を隠す。スマホのスキー場詳細の小さい地図にも同じ「営業中のみ」「投稿」「＋投稿」と出典を1行で置き、幅が足りないときは出典だけを1段上の右端へ回す。投稿を取得できない、またはそのスキー場の投稿が1件もない場合、「投稿」は「営業中のみ」と同じく半透明にして押せなくする。投稿中のスマホの地図には拡大・現在地・営業フィルターを出さない。スキー場詳細の「投稿」タブは、1段目に表示期間（全期間・今シーズン・過去1週間・過去3日）・表示する項目（すべて・コース・リフト）・並び順・青い「＋投稿」、2段目に滑走日の開始〜終了を置く。表示期間を選ぶとその期間の日付（全期間は空）が入り、日付を手で変えて当てはまる期間がなければ「期間指定」と表示する。「今シーズン」は9月末で区切り、10月1日から今日までの滑走日を対象にする（地図の投稿表示も同じ）。投稿を押すと、詳細のコース選択とは別に、その投稿のコース・リフトを地図で強調し、場所があれば印を出す（もう一度押すと解除）。投稿を押すたびに、保存済みの表示範囲や同じ対象の選び直しに関係なく、その対象へ地図を寄せる。コース・リフトがない投稿や、投稿のコースが今の地図データにないときは場所へ寄せる。スマホの投稿タブには地図をタブの下に貼り付けて出し、地図の操作ボタンは出さない。投稿カードは投稿者名を太字で大きく出し、右上に「滑走日時」、下にコメントといいねのアイコン（件数付き、高さ36pxの押しやすい範囲）と右端に「投稿日時」（日本時間）を並べる。320pxのスマホではボタンの間隔を詰めて1行に収める。「投稿の詳細」リンクは置かない。いいねは押した瞬間に表示を切り替え、失敗したら戻す。コメントのアイコンでその場にコメント一覧と入力欄を開く。いいね・コメントは押した時点でログインを確かめ、未ログインならGoogleログインへ進めて元の画面へ戻す（戻り先はサイト内の画面に限る）。写真を押すと、後ろが透ける薄い背景の真ん中に写真を浮かべて拡大表示し、×は写真の右上に置く。動きは付けず、読み込み前から縦横比で大きさを決め、読み込み済みの小さい写真を敷いて表示が広がらないようにする。スマホは画面全体、PCは詳細パネルの範囲に重ねる。一覧・写真一覧・投稿フォームの小さな写真は `?size=thumb`（320px）で受け取り、元の写真（最大2048px）は拡大表示だけで読み込む。投稿フォームのコース・リフトは、スキー場詳細で読み込み済みの地図データから作り、開くときに取り直さない。ログインしているかはブラウザが持つログイン状態で判定し、未ログインなら投稿画面の中に「現地レポートを投稿するにはログインが必要です」と「Googleでログイン」を出す（サーバーへの問い合わせはしない）。ログインは別ウィンドウ（スマホでは新しいタブ）で行い、終わったら閉じて元の画面はログイン状態だけを読み直すので、地図や開いている画面を読み込み直さない。別ウィンドウを開けないとき、または元の画面がもう開いていないときは、投稿画面を開いた状態のスキー場詳細へ戻る。開発環境で未ログインのまま入力画面を確認するときは、ブラウザの localStorage に `rusutsu:composer-preview` = `1` を入れる（送信はできない）。サーバーでの照合も同じ地図を使い、連携エリアの子では詳細と同じく親の地図のコース・リフトを受け付ける。

## データ・写真

初期追加は `prisma/migrations/20261024000000_community_contributions/migration.sql`、日次レポートへの再設計は `prisma/migrations/20261025000000_daily_visit_reports/migration.sql`。公開前・未投稿の構造変更として、旧分割投稿の列を廃止し、子項目テーブルを追加する。旧形式の投稿データを取り込む移行処理は設けない。新規モデルは親レポート `CommunityPost`、子項目 `CommunityEntry`、`CommunityComment`, `CommunityLike`, `CommunityNotification`, `CommunityReport`, `CommunityModerationJob`, `ContributionPhoto`, `ContributionRateBucket`。`User` に公開名・選択方式・管理者による投稿停止日時、`EditRequest` に送信キーと写真関連を追加する。

投稿写真は必ず項目に付ける（`photos:<項目のclientKey>` だけを受け付け、項目に紐づかない写真はDB制約でも拒否する）。項目を消すと写真も消える。1枚8MiB以内、1件の投稿で6枚まで（合計最大48MiB）。2026-10-26の `20261026000000_report_entry_photos` マイグレーションで `ContributionPhoto` を項目へ関連付ける。ブラウザはアップロード前に写真のGPS情報を端末内で読み取り、場所が未指定なら反映する。コース・リフトが未選択なら最も近いものを選び、コブ・パークではその地点に最も近いコースを選ぶ。2026-10-26の `20261026120000_single_item_reports` マイグレーション（投稿が1件もない前提。時刻列をNOT NULLで追加するため、投稿が残っていれば失敗して止まる）で、上記の旧列を削除し、時刻・リフト速度・コブの深さの列を追加し、コース・リフトにも位置を保存できるよう制約を変更する。保存前に画像を検証し、2048px以内のWebPへ変換してEXIF/GPS・元ファイル名を除去する。GPSがない写真では地図から場所を選ぶ。画像を `public` 配下や外部ストレージへ出さない。専用配信ルートが公開状態・管理者権限を確認し、`no-store` を返す。アカウント削除で写真実体・投稿・コメント・星・いいね・プロフィール等をDBの外部キーで削除する。匿名の修正依頼はアカウントと結び付けない。

投稿中はPC・スマホともスキー場のヘッダーを出さず、既存と同じ見た目の×だけを置く。最初のページで種類（コース・リフト・コブ・パーク）を選び、次のページで1項目を入力して投稿する。投稿後は「投稿ありがとうございます」と「別の投稿をする」を表示し、押すと種類の選択へ戻る。PCではスキー場詳細の右パネル、スマートフォンでは詳細の地図の下（コース詳細と同じ位置）に投稿画面を出し、どちらも既存の地図をそのまま使う。地図でコース・リフトを押すと対象になり、種類の選択中なら押した種類の投稿を始める。コブ・パークでは地図を押した地点が場所になる。コース・リフトの場所は「地図で選ぶ」を押してから地図で指定する。種類の選択では「どの項目についてレポートしますか？」と添える。日時と、コース・リフトの状況は必須。各項目名の下に小さく「必須」「任意」を書き、数値の欄には薄く「任意」と表示する。「投稿する」は常に押せ、必須項目が足りなければ各欄の下と送信ボタンの上に警告を出して最初の欄へスクロールする。リフトの速度はm/sとkm/hの欄を並べ、片方を入れるともう片方を小数第1位で換算して表示する。数値の欄は上下の矢印やホイールで値が変わらないよう、数字だけを受け付ける文字欄にする。入力を変えた後に×を押すと、内容が消えることを確認してから閉じる。×で閉じると投稿を始める前の選択に戻して元の詳細を出す。投稿URL `/community/[resortId]/new` はスキー場詳細内の投稿画面へリダイレクトする。動画・自然地形のジャンプスポット・体感難易度・当日の営業情報の手動変更は対象外。

開発環境では、投稿APIを利用できない場合や公開名が未設定の場合に、入力・確認画面だけのプレビューを表示できる。プレビューでは認証情報を偽装せず、投稿・更新などの書き込みを行わない。実際の投稿には本番OAuthでログインしたアカウントが必要。

`DATA_API_BASE_URL` が設定されている環境では、`features/community/actions.ts` は入力検証とAPI呼び出しを行うラッパーで、投稿の業務処理は `server/community/operations.ts` にある。書き込み・読み込みは `/api/internal/v1/community` へ送り、既存の `INTERNAL_DATA_API_ADMIN_TOKEN`（`admin-data` scope）で認証する。APIを呼べない場合にローカルDBへフォールバックしない。ローカルサイトのGoogle認証アダプターはローカルの `users` / `accounts` を使い、ローカル `community_*` テーブルは投稿データに使わない。投稿APIサーバーはGoogleの `providerAccountId` を本番の既存 `accounts` と照合し、対応する本番ユーザーIDで処理するため、投稿前に本番サイトでGoogleログインを完了しておく。リモートデータモードではローカルのコミュニティモデレーションスケジューラーを起動しない。

写真は入力欄の先頭で追加する（端末のカメラでの撮影も選べる）。最初の有効な写真のEXIF撮影日時（DateTimeOriginal、なければDateTimeDigitized）を日時の初期値とし、同じ欄で変更できる。手動で変更済みの日時や編集中の投稿の日時は写真追加で上書きしない。撮影日情報がない写真や未来の日付ではアップロード日時やファイル更新日時から推測しない。GPSと撮影日は元の写真からブラウザ内で読み取る。HEIC／HEIFはサーバー内の専用デコーダーでWebPへ変換してプレビュー・投稿に使う。写真を変換するために外部サービスへは送信しない。保存画像からは従来どおりEXIFを除去する。

## 初期設定

1. 実際に保存する環境では、投稿APIを含むサーバーをデプロイし、投稿APIが接続する正本DBへコミュニティマイグレーションをすべて適用する。アプリ側の型生成が必要な場合は `mise run db:generate` を実行する。ここでは本番DBへの適用は実行していない。
2. Google OAuthは既存設定を再利用する。新しいプロバイダーは不要。Google認証設定は変更しない。リモート投稿では、ローカルの認証セッションに対応する `providerAccountId` が本番 `accounts` に存在する必要がある。
3. 本文の外部AIチェックを使う場合はサーバーの `OPENAI_API_KEY` を設定する。APIは [OpenAI Moderation](https://developers.openai.com/api/docs/guides/moderation) の `omni-moderation-latest` を使う。外部へ送るのは本文だけで、写真は送らない。
4. 写真もAI確認するには、**サイト内ネットワークで運用するAI判定サービス**を用意し、`COMMUNITY_MODERATION_URL`（例 `http://moderation:8080/v1/moderations`）を設定する。必要なら `COMMUNITY_MODERATION_TOKEN` と `COMMUNITY_MODERATION_MODEL` を設定する。URLはループバック・プライベートIPv4・コンテナ名に制限し、外部URLとリダイレクトを拒否する。
5. AIサービス未設定・失敗時も投稿は即時公開され、管理画面で未処理・失敗を確認できる。写真用サービスがない場合、本文の確認結果と写真の確認待ちを区別して残す。判定サービス自体のモデル運用はこのリポジトリには含めない。
6. `CONTRIBUTION_TRUST_PROXY=true` は信頼するプロキシが **常に X-Real-IP を上書きする構成だけ**で設定する。既定はfalse。通常の匿名送信には追加操作を求めず、短時間の連投だけブラウザ内の計算確認を行い、DB共有の頻度制限も適用する。

Docker ComposeとGitHub Actionsにも設定を渡す。APIキー・サービス用トークンは同名のGitHub Secrets、URL・モデル・プロキシ設定は同名のVariables。未指定の任意設定は既存コンテナから引き継ぐ。サービス判定JSONはOpenAI Moderation互換の `results: [{ flagged: boolean, categories: {...}, category_scores: {...} }]`。判定リクエストは `{ model, input: [{type:'text', text}, {type:'image_url', image_url:{url:'data:image/webp;base64,...'}}] }`。画像を外部へ転送しないサービスを運用すること。

## 確認手順

- `http://localhost:3000/rusutsu` でスキー場を開き、修正を匿名で送信。公開画面に反映されていないことを確認する。
- `/rusutsu/admin/corrections` で投稿時・現在・提案を比較し、候補調整と項目ごとの承認・却下を行う。別画面で先に値を変えた場合は競合として拒否される。
- 未ログインで「＋投稿」を開くと、Googleログインとなる。公開名の初回設定後、種類を選び、写真・日時・場所と種類ごとの欄を入力して投稿する。GPS・撮影日時付きの写真を追加すると日時・場所・近いコース／リフトが入ることを確認する。「別の投稿をする」で種類の選択へ戻る。
- レポートを編集し、項目の入力と写真の更新を確認する。別ユーザーでコメント・いいねを行い、子項目の追加・状態変更をレポート単位で確認する。地図の「投稿」は既定OFFで、現地確認日・種類で切り替える。
- 別アカウントで投稿・コメント編集ができないこと、修正根拠写真が管理者以外には404になることを確認する。
- アカウント削除後に本人の写真URLが404になることを確認する。

## 検証と制約
