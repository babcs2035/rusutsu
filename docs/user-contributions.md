# ユーザー投稿機能

2026-10-25 時点の実装と運用手順。既存の編集者向け申請とは入口を分け、匿名の情報修正には `EditRequest.kind = public-correction` を使う。公開投稿は1回の現地訪問を表す親 `CommunityPost` と、内容別の子 `CommunityEntry` に保存する。

## 画面と保存先

| 機能 | 入口・実装 | 保存・審査 |
| --- | --- | --- |
| 匿名の修正提案 | 詳細の「情報を修正する」、`/corrections/[resortId]` | `EditRequest` / `EditRequestEvent`。承認前は正式データを変更しない |
| 基本情報・関連URL | 基本情報、`/corrections/[resortId]/links` | スキー場マスターまたは既存 `SkiResortLinks.json` 文書への項目単位CAS |
| コース・リフト情報、一括修正 | 修正トップから対象・項目を選択 | 変更なしの行を含めて送信し、審査時に変更なしと区別 |
| 位置・追加・削除、属性の区間設定 | 修正内の地図 | 元座標を保存。スナップ・線の統合なし。属性区間は0〜1の距離比率で別々に保存 |
| 料金・出典の報告 | 計算結果・価格セル・出典表記の操作 | 条件・結果・識別子を非公開添付。管理者が確認して元データを修正 |
| 管理者による調整・部分承認 | `/admin/corrections` | 提出内容・候補・実際の反映を分離。元データと申請版が変わっていれば拒否 |
| 滑走レポートと項目 | `/community/[resortId]`、詳細の「投稿」タブ、地図の「＋投稿」 | Googleログインと公開名設定後、1レポートを即時公開 |
| レポート項目 | 1つのレポートにCOURSE・LIFT・MOGUL・ITEMを複数追加 | 子 `CommunityEntry` に保存。同じコース・リフトはレポート内で重複不可 |
| コメント・いいね・通報・通知 | 投稿詳細、ホームのアカウント | 投稿者の認可・版を検証。匿名通報可。通知はサイト内のみ |
| 公開名・履歴・削除 | `/profile/[id]`、`/account/community` | Google名・ニックネーム・匿名。メールと選択していない本名を公開しない |
| AI・管理者対応 | `/admin/community` | 永続キューで事後判定。古い版の判定は新しい編集に適用しない。停止は管理者だけ |

現地確認日・全体の感想・全体評価は親 `CommunityPost` に保存し、各項目の感想・状態・項目評価は子 `CommunityEntry` に保存する。項目種別はCOURSE、LIFT、MOGUL（コブ）、ITEM（パーク設備）。コースとリフトは地図または選択欄から選び、コブとパーク設備は地図上の位置を記録する。いいね、コメント、通知、AI判定、非表示、削除はレポート全体を単位とする。

公開地図では下部パネルの上に「営業中のみ」「投稿」「＋投稿」と地図の出典を独立した1行で配置する。投稿レイヤーには子項目（コブ・パーク設備）の位置を表示し、選択すると親レポートの詳細へ移動する。パネル内は上段が凡例・フィルター、下段が難易度／斜度・背景・設定。営業中のみONではコース凡例を○・△・不明の選択へ置き換え、投稿ONでは投稿期間・種類を優先する。狭い幅では投稿フィルター表示中のリフト凡例を隠す。

## データ・写真

初期追加は `prisma/migrations/20261024000000_community_contributions/migration.sql`、日次レポートへの再設計は `prisma/migrations/20261025000000_daily_visit_reports/migration.sql`。公開前・未投稿の構造変更として、旧分割投稿の列を廃止し、子項目テーブルを追加する。旧形式の投稿データを取り込む移行処理は設けない。新規モデルは親レポート `CommunityPost`、子項目 `CommunityEntry`、`CommunityComment`, `CommunityLike`, `CommunityNotification`, `CommunityReport`, `CommunityModerationJob`, `ContributionPhoto`, `ContributionRateBucket`。`User` に公開名・選択方式・管理者による投稿停止日時、`EditRequest` に送信キーと写真関連を追加する。

写真は1枚8MB以内、レポート共通で6枚まで、匿名修正1件3枚。レポートの写真合計は48MBまで。実体を検証し、2048px以内のWebPへ変換、EXIF/GPS・元ファイル名を除去してDBに保存する。画像を public 配下や外部ストレージへ出さない。専用配信ルートが公開状態・管理者権限を確認し、`no-store` を返す。アカウント削除で写真実体・投稿・コメント・星・いいね・プロフィール等をDBの外部キーで削除する。匿名の修正依頼はアカウントと結び付けない。

投稿画面はPCでは左にGSI地図、右に入力フォームを表示する。スマートフォンではフォーム全体をスクロールでき、地図選択時はGSI地図をポップアップ表示して背景入力を保持する。写真は1つの親レポートにまとめて添付する。動画・自然地形のジャンプスポット・体感難易度・当日の営業情報の手動変更は対象外。

## 初期設定

1. 通常の接続先を確認して `mise run db:generate`、`mise exec -- pnpm prisma migrate deploy` を実行する。ここで本番DBへの適用は実行していない。
2. Google OAuthは既存設定を再利用する。新しいプロバイダーは不要。新レポート対応でGoogle認証設定と公開名設定フローは変更しない。
3. 本文の外部AIチェックを使う場合はサーバーの `OPENAI_API_KEY` を設定する。APIは [OpenAI Moderation](https://developers.openai.com/api/docs/guides/moderation) の `omni-moderation-latest` を使う。外部へ送るのは本文だけで、写真は送らない。
4. 写真もAI確認するには、**サイト内ネットワークで運用するAI判定サービス**を用意し、`COMMUNITY_MODERATION_URL`（例 `http://moderation:8080/v1/moderations`）を設定する。必要なら `COMMUNITY_MODERATION_TOKEN` と `COMMUNITY_MODERATION_MODEL` を設定する。URLはループバック・プライベートIPv4・コンテナ名に制限し、外部URLとリダイレクトを拒否する。
5. AIサービス未設定・失敗時も投稿は即時公開され、管理画面で未処理・失敗を確認できる。写真用サービスがない場合、本文の確認結果と写真の確認待ちを区別して残す。判定サービス自体のモデル運用はこのリポジトリには含めない。
6. `CONTRIBUTION_TRUST_PROXY=true` は信頼するプロキシが **常に X-Real-IP を上書きする構成だけ**で設定する。既定はfalse。通常の匿名送信には追加操作を求めず、短時間の連投だけブラウザ内の計算確認を行い、DB共有の頻度制限も適用する。

Docker ComposeとGitHub Actionsにも設定を渡す。APIキー・サービス用トークンは同名のGitHub Secrets、URL・モデル・プロキシ設定は同名のVariables。未指定の任意設定は既存コンテナから引き継ぐ。サービス判定JSONはOpenAI Moderation互換の `results: [{ flagged: boolean, categories: {...}, category_scores: {...} }]`。判定リクエストは `{ model, input: [{type:'text', text}, {type:'image_url', image_url:{url:'data:image/webp;base64,...'}}] }`。画像を外部へ転送しないサービスを運用すること。

## 確認手順

- `http://localhost:3000/rusutsu` でスキー場を開き、修正を匿名で送信。公開画面に反映されていないことを確認する。
- `/rusutsu/admin/corrections` で投稿時・現在・提案を比較し、候補調整と項目ごとの承認・却下を行う。別画面で先に値を変えた場合は競合として拒否される。
- 未ログインで「＋投稿」を開くと、Googleログインとなる。公開名の初回設定後、現地確認日・全体の感想と評価を入力し、「＋コース」「＋コブ」「＋パーク」「＋リフト」で項目を追加する。項目は折りたたみ・再展開・削除できる。スマートフォンでは項目追加時に地図ポップアップが開き、対象・位置を選んで「選択を確定」する。内容確認後、1回の送信で親レポート1件を投稿する。
- レポートを編集し、項目の追加・削除、全体と項目の入力、写真の更新を確認する。内容確認画面から1回で更新できることを確認する。別ユーザーでコメント・いいねを行い、子項目の追加・状態変更をレポート単位で確認する。地図の「投稿」は既定OFFで、現地確認日・種類で切り替える。
- 別アカウントで投稿・コメント編集ができないこと、修正根拠写真が管理者以外には404になることを確認する。
- アカウント削除後に本人の写真URLが404になることを確認する。
