# 編集者と承認フロー

## 第1段階：アクセス権限

Google 認証後の権限は閲覧者，編集者，管理者の 3 種類である．画面と Server Action は現在の DB 権限を確認する．

編集者は全施設の編集申請を作成できる．編集対象を施設への所属で限定する設定は設けていない．申請の参照と取り下げは本人に限定し，承認と公開への反映は管理者が行う．

| 操作 | 閲覧者 | 編集者 | 管理者 |
| --- | --- | --- | --- |
| 公開情報の閲覧 | 可 | 可 | 可 |
| 6種類の編集ツール | 不可 | 可 | 可 |
| 編集結果の直接反映 | 不可 | 不可 | 可 |
| 自分の申請の確認・取り下げ | 不可 | 可 | 管理者として確認 |
| 全員の申請の確認・修正・承認・却下 | 不可 | 不可 | 可 |
| ユーザー一覧・メールアドレス・権限変更 | 不可 | 不可 | 可 |
| クローラー画面・実行・診断 | 不可 | 不可 | 可 |
| 確認済みフラグ・標高の再取得・スキー場統合 | 不可 | 不可 | 可 |

編集者のダッシュボードではユーザー一覧を取得しない。申請の取得条件にも本人のIDを指定し、他人の申請や管理者の修正案を編集者へ返さない。クローラー関連ページも管理者を確認する。

## 第2段階：申請の保存

編集者の保存操作は、スキー場情報・リンク・リフト・コース・リフト券・レビューのすべてで申請になる。コースの並び順、営業情報の対応表、レビューJSONのアップロードも対象。

既存の検証・変換処理を使って反映予定のデータを準備し、公開DBへの書き込みと標高の取得は行わない。リフト・コースと関連リンクは同じ申請にまとめる。

保存するものは、提出時の入力、変更前のデータと版、反映予定のデータ、管理者が修正する候補、申請状態、操作履歴。提出時の入力は、管理者による修正後も保存する。

申請状態は「承認待ち」「反映済み」「却下」「取り下げ」「競合」。1人の承認待ち申請は最大100件。入力の大きさ・構造・対象IDをサーバーで検証する。

## 第3段階：管理者の修正と承認

管理者は申請詳細で変更前との差分とリフト・コースの地図を確認し、項目をその場で修正できる。「修正内容を検証・保存」では公開情報は変わらない。保存した修正案を確認後、「承認して反映」で公開する。

対象のスキー場IDや編集元の版は変更できない。修正画面は既存項目の変更に対応し、項目・行の追加や削除を伴う作り直しは編集ツールから改めて申請する。

承認時には、管理者と申請者の現在の権限、申請の状態と版、変更前データのハッシュ・版・更新日時を再確認する。古い申請で新しい公開情報を上書きしない。公開データ、申請の「反映済み」、操作履歴、標高更新ジョブを同じDBトランザクションで確定する。

同時承認、承認と取り下げの競合では、1つの操作だけが成立する。途中のDB処理が失敗すると全体を取り消す。公開データの競合時は申請・管理者の修正案を保持し、管理者に現在の公開内容との差分を表示する。「申請・修正内容を採用」で修正案を反映するか、「現在の公開内容を残す」で申請を却下して公開内容を維持するかを選べる。再申請は不要。採用時も管理者・申請者の現在の権限と申請の版を再確認し、反映と操作履歴を同じトランザクションで確定する。

競合した修正案を採用するときは、共有JSON内の別スキー場や、変更していない項目、同時に追加された別のコース線を保持する。変更した項目が競合する場合は、管理者が選択した修正案を優先する。

編集者は管理者が修正した内容の再承認を求められず、「反映済み」で完了する。却下には理由が必須。

## 第4段階：標高更新と運用

標高の外部取得は承認後に行う。ジョブをDBに保存し、起動時と毎分に実行する。複数サーバー間の同時実行をPostgreSQLのロックで防止し、最大5回試行する。対象データが後から変わっていれば古いジョブを破棄する。

`DISABLE_EDIT_REQUEST_JOBS=true` で標高ジョブの実行を停止できる．

## ローカルから正本を編集する

`API_BASE_URL` を設定した環境では，ローカルサーバーが `API_BEARER_TOKEN` で `POST /rusutsu/api/admin/edit-requests` を呼ぶ．申請，修正案，操作履歴と標高ジョブは接続先の DB に保存する．

ログイン済みユーザーの Google アカウント識別子を，ローカルサーバーが取得して送る．接続先は自分の DB にあるアカウントと照合するため，両環境のユーザー ID が異なっていてもよい．編集には両環境で編集者または管理者の権限が必要である．修正・承認を行う管理者は，両環境で管理者の権限を持つ必要がある．

競合内容を採用する場合は `approve` に `overwrite: true` を指定する．通常の承認では省略する．アプリと接続先 API は対応する版を使う．

## 検証

```sh
mise run test -- --db src/server/edit-requests/workflow.integration.test.ts
```

使い捨て DB で，公開情報と申請の同時確定，降格，所有者の制限，同時承認，版の競合，失敗時の取り消しを確認する．リモート試験は同じ試験 DB の別 schema を使い，接続先だけに保存することを確認する．
