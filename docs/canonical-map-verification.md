## 変換検証の結果

対象文書を持つ451スキー場を、実際のPrisma変換処理とローカルDBで検証。
各スキー場の変換後に座標・Feature件数・ID・非空の編集元属性を照合し、
試行ごとにロールバックした。449件が成功、次の2件は既存の標高線の対応不整合で停止。

| スキー場 | 対応できない標高付きFeature（0始まりのindex） |
| --- | --- |
| `hoshino-resorts-nekoma-mountain` | 27, 28, 29, 32, 33, 34 |
| `tazawako` | 6, 7 |

これら8本は標高側のentityIdが編集元に存在せず、同名線も複数あるため、
名前だけで一意に対応付けられない。自動でIDを書き換えたり、線を削除したりしていない。
全件の実CLIのdry-runでも同じ8件が出る。
ローカルDBでapplyが書込み前に拒否されることと、元の1,516文書の
key/hash/versionが変わらず、切替マーカーも作成されないことを確認した。
初回時点では、この不整合によって全件切替を完了できなかった（上記で解消済み）。

別途、`kamui-ski-links` の対応表にマップ上の相手がない名称が2件あった。
未対応の公式行として保持する対象で、移行の停止理由ではない。
