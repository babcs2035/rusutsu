# 複数件・全スキー場・再開

複数件を実行するときに読む。全件を対象一覧へ固定し、施設ごとに現在の段階を
保存する。チャットの記憶やURL登録の有無だけで完了を判断しない。
この手順はエージェントが台帳を更新しながら実行するもので、自動スケジューラ
やバックグラウンドサービスを作成・起動する指示ではない。

## 対象と実行範囲を固定する

1. 現在のマスタからID・名称・所在地・公式サイト・統合関係を読み取り、対象一覧
   を作る。利用可能な既存API・Prisma読み取り経路を使い、取得元と取得日時を記録
   する。既存料金JSONのある6件などを全スキー場の母集団にしない。
2. 全件依頼では有効な既存マスタを対象にする。`isActive: false`、統合済みの
   `MERGED` 子、重複IDを除外し、そのIDと理由も残す。`LINKED` の子や共通券
   グループを機械的に除外せず、既存の料金参照先・統合方式を確認して対象を決める。
   参照先を確定できない施設だけ `needs_review` にする。公式URLなしは探索対象。
3. `run-id`（日付と用途等、一意な名前）、対象シーズン、依頼のモードと終了段階を
   決める。指定URL限定なら許可URL集合も各ジョブへ保存する。途中で新たな対象を
   自動追加しない。追加依頼は台帳に履歴を残す。
4. `templates/batch-run.template.json` を
   `src/private/data/lift-ticket-workflow/{run-id}/run.json` へコピーし、対象を記入する。
   全件数、対象件数、除外件数が照合できるようにする。マスタの生スナップショット
   は `src/private/data/resorts-temporary/tmp/lift-ticket-batch/{run-id}/` に保存する。

モードは `discover_only` / `collect` / `audit_only`。
終了段階 `target_checkpoint` はURL調査なら `urls_verified`、草案のみなら
`extracted`、本番へ反映しない
収集・監査なら `tested`、本番反映まで含む依頼なら `published`。
試行依頼は `tested` を上限とし、URL調査の試行なら `urls_verified` まで。
`publish_authorized` に今回の依頼から本番書込みの範囲を記録する。Skillの説明や
台帳テンプレートだけを本番反映の許可と解釈しない。既に依頼された範囲内での
バッチ続行やURL追加について再承認は不要。

## 台帳のジョブ

`jobs` は対象IDごとに次のレコードを1件持つ。例は構造説明用で実施設ではない。
空欄は実行時に記入する。料金JSONのSchema・taxonomyとは別の運用台帳である。

```json
{
  "resort_id": "example-resort",
  "name_ja": "例示スキー場",
  "status": "pending",
  "checkpoint": "pending",
  "current_stage": null,
  "allowed_urls": null,
  "attempts": 0,
  "updated_at": null,
  "reason_ja": null,
  "retry_after": null,
  "missing_items": [],
  "review_questions": [],
  "artifacts": [],
  "quality_status": null,
  "publish_result": null,
  "history": []
}
```

| checkpoint | 到達条件 |
| --- | --- |
| pending | 未着手 |
| urls_verified | Stage 0の全項目を確認し、採用URL・不足・対象シーズンの状況を保存した |
| captured | 採用資料の取得成功と対象シーズンmatchを確認した |
| extracted | 草案を作り、機械検証3本が通った |
| audited | 独立監査の誤りを修正し、機械検証3本を再通過した |
| tested | 公式から独立に期待値を作ったUI共通照合と必要なCI固定資料テストが通った |
| published | 対象の確定版を本番へ反映、または本番と同内容であることを確認した |

`checkpoint` は証拠を確認できた最後の段階。開始時に `current_stage` を記録し、
その段階の資料・結果が揃ってからcheckpointを進める。
`artifacts` には相対パス・SHA-256・対象段階を記録する（登録URL、manifest、草案、
監査、テスト結果、確定版等）。秘密情報・トークン・Cookie・認証済みURLは保存しない。
テストケース・実行結果は作業領域へ保存し、`history` には段階・日時・結果を残す。

`status` は進行・保留の状態:

- `pending`: 未着手。
- `running`: 処理中。
- `completed`: 今回の終了段階まで到達し、保留すべき未解決事項がない。
- `deferred`: 今季未発表等、公式更新待ち。確認できた旧シーズンと再確認先を残す。
- `needs_review`: 施設同定、シーズン矛盾、判読不能、料金計算を左右する未解決事項、
  独立監査を実行できない等。質問・根拠・再開する段階を `reason_ja` 等に残す。
- `failed`: 取得・処理・検証に失敗し、今回の試行では解消できない。

URL確認完了、テスト完了、本番反映完了の件数はcheckpoint別に数える。
`discover_only` のcompletedを「料金収集完了」と呼ばない。`quality_status` と
実行statusは別で、`needs_review` のデータを本番反映できた場合も、その品質と
未解決事項を明示する。`retry_after` は再確認の目安で、自動予約を意味しない。

## 小分けで実行する

- 既定のバッチサイズは5件。対象が少なければ全件、試行では指定件数まで。
  指定があれば従う。全件依頼では5件ごとの報告後も次の未完了施設へ進む。
- 最初の試行は施設を1件ずつ最後まで通す。全国処理でも同時に抽出する施設は
  既定で最大2件とし、利用可能なエージェント数に合わせる。施設の並列数と
  取得＋抽出/独立監査の分担は別。監査を省略して並列数を増やさない。
- メイン担当だけが台帳、MISSING.md、本番反映を更新する。サブ担当は割り当てた
  施設の資料・草案・監査結果を扱い、同じ施設の同じ段階を重複実行しない。
  監査担当には保存資料・草案・チェックリスト・taxonomyだけを渡す。
- 一施設の段階が終わるたびに台帳を保存する。施設ごとのStage 0から本番反映は
  SKILL.mdの通常手順を使い、一括反映・一括削除へ置き換えない。
- 計算に影響する未解決事項はSKILL.mdどおり1件1文で質問し、回答がない施設を
  `needs_review` にして他の施設を進める。回答待ちを推測で解決しない。
  今季未発表なら旧料金をコピーせず `deferred` にし、既存の確定版・本番を保持する。
- 同じ原因の失敗は、方法変更による再試行を含め1施設につき連続2回までとする。
  解決できなければ保留して次へ進む。認証・マスタ取得・共通検証スクリプト等の
  共通障害なら影響段階を止め、独立して進められるURL探索等だけ続ける。

## 再開・変更・後片付け

1. 指定されたrun.jsonを読み、同じ施設・シーズン・依頼範囲か確認する。
   別シーズンは別runにする。現在のマスタと差異があれば同定・統合関係を見直す。
2. `running` のままなら中断した可能性がある。別担当が処理中でないことを確認し、
   保存資料・草案・監査・テスト結果の存在とSHA-256を照合する。
   台帳だけを根拠に段階を飛ばさない。記録のない結果は確認できる段階から再実行する。
3. URLや取得資料が変われば抽出以降をやり直す。草案が変われば検証・監査・テストを
   やり直す。履歴を残してcheckpointを有効な段階へ戻す。
   更新・監査の本番pullは現行手順どおり行い、前回pull後の管理画面変更を
   見落とさない。ローカル変更との競合があれば保留し、上書きしない。
4. `completed` は既定で再処理しない。更新依頼、公式更新、資料変更、品質の未解決
   があれば対象を再選定する。`deferred` / `needs_review` / `failed` は理由を解決
   できるときだけ再試行し、同じ実行内で保留施設を無限に再選択しない。
5. 本番反映直前のプレビュー・変更検知は毎回行う。途中で本番やローカルが
   変わっていたら既存のpublish手順に従いプレビューからやり直す。
6. 本番反映（または本番同内容）と台帳保存が終わった施設の抽出作業領域だけを
   通常手順で削除する。他シーズンや別runが同じ施設の作業領域を使用中なら、
   使用している部分を削除しない。未反映・保留の資料は残す。
   URL探索資料も、確認内容・不足の要約を台帳へ残した後、反映済み施設分だけ
   削除できる。台帳と登録URL、確定版は残す。
   削除する一時資料のパスとSHA-256は履歴として残すが、現在の有効なartifactsからは
   外す。publishedの再開確認は残した確定版と本番を使い、削除済み資料を要求しない。

## バッチ報告と完了

各バッチ終了時と中断時に、台帳パス、今回処理した施設、URL確認/テスト/本番反映の
件数、残件数、保留施設と理由・質問を短く報告する。URL調査だけ・試行・本番未反映を
区別する。資料削除後も追えるよう `history` に反映結果・不足を残す。

今回の対象を一巡したらrunの `status` を `completed` または
`completed_with_holds` にする。中断時は `stopped`。全件処理を「全件の料金が揃った」
と表現せず、対象総数、終了段階へ到達した件数、保留・失敗・除外を報告する。
保留理由と再開先を残し、次回は同じ台帳から再開できるようにする。
