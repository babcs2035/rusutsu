# Implementation guidelines

抽出ロジックの実装・修正・監査時に使う、サイト固有の判断基準と出力規則。

## DOMとセレクター

- 本番と同じPlaywright・localeで `domcontentloaded` 後に対象要素の `attached` を待つ。Ajaxで必要な場合だけクリックや追加待機を行う。
- 非表示タブ内に対象DOMが存在するなら、抽出のためだけのクリックは不要。
- 調査資料は操作後の `page.content()` とconsole errorに限定する。console errorは抽出への影響を内容で判断する。
- セレクターは、固有ID／`data-*`、見出しを含む親、役割を示すclass・属性、親子関係、固定位置の順に検討する。
- 表は可能なら正規化した `th` から列indexを求め、先頭行だけ構造が違わないかも確認する。固定列に依存する場合は、見出しが使えない根拠をコメントに残す。
- `shared` を使わない旧形式を設計基準にしない。参考例は `hakuba-happo-one.ts`、`kiroro-snow-world.ts`、`geto-kogen.ts`、`kagura.ts`。

### 運用中の診断DOM

- 新規実装・修正時にセレクターを調査するためのDOM保存と、運用時の自動診断保存を区別する。
- 運用時は正常かつ無警告のDOMを保存しない。例外、navigation失敗、必須selector消失、想定外の生値、空名・重複・件数異常、不正URL、クローラープロセスの `console.warn` / `console.error` を診断対象とする。公式ページ内のJavaScriptが出すconsole/page errorは広告等のノイズも多いため単独では保存トリガーにせず、診断DOMが別の理由で保存された場合の補助情報にする。
- 診断データには実行ID、スキー場ID、発生時刻、原因、対象URL、クローラーrevision、同時点のレンダリング済みHTMLを含め、後からAIがローカルに取り出せる形にする。Cookie、Authorization header、API key、フォーム入力などの秘密値は記録しない。
- DOM保存自体の失敗で元の原因を隠さない。診断保存を待ってからbrowserを閉じ、保存失敗も別の警告として残す。
- input（typeにかかわらず）、textarea、selectのフォーム値は取り除く。CookieやAuthorization headerは収集しない。URL内の認証情報やtoken/query、HTML内の秘密値も共有redactionを通す。
- remoteモードのDOMと生結果はworkerではメモリだけに保持する。APIへgzipを送信してからrunを記録し、アップロードだけ失敗した場合も元issueとDOM保存失敗メタデータの登録を試す。API全体への通信が失敗した場合は非0終了として扱い、保存済みと報告しない。
- `CRAWLER_ARTIFACT_ROOT` の解決はCLI dotenv読込み後に行う。既定30日（`CRAWLER_ARTIFACT_RETENTION_DAYS`）を過ぎたDOMの参照を失効させ、孤立gzipをGCで削除する。run/issue/hashは保持する。DOMのないbrowser launch失敗や期限切れrunも診断APIからメタデータを取得できる。
- エラーの有無とカテゴリの良否を分ける。正常データが作れた場合はカテゴリごとにAPIで再検証し、影響カテゴリだけ昇格を止める。カテゴリ不明の取得・検証issueは全カテゴリを保留する。診断保存issueだけなら正常カテゴリは更新できる。
- 明示的に「その公式ページには存在しない」と検証済みのカテゴリや値は警告にしない。「存在するはずなのに取れない」場合だけ必須DOM消失として扱う。

## 冬季アーカイブ

現在がオフシーズン、または現在DOMのカテゴリ・値・行が空なら、同じ公式URLの直近営業中のスナップショットを確認する。通常は12〜3月、春営業主体なら4〜5月も対象にする。カテゴリ別にURLが分かれる場合は各URLを調べる。

- アーカイブもPlaywrightで開き、完全HTMLとconsole errorを `crawl_latest_dom/<resort-id>/archive-<timestamp>/` に保存する。
- 現在と同じセレクターまたは抽出関数を適用し、カテゴリ、名前、状態、件数、更新日時を機械的に照合する。
- Waybackツールバーを公式DOMと誤認しない。最寄りの別日時へリダイレクトされた場合は最終日時を記録する。
- スナップショットなし、リプレイ不能、JS/API欠損は「未確認」とする。休業表示しか確認できないものを合格扱いしない。
- アーカイブ値は現行値ではない。ただしクローラーが正常保存した検証JSONは比較資料として残す。

### 空欄の状態は不明

コース・リフトの状態欄が空欄なら `status: null` とする。空文字、空白のみ、`-`・`-----`・`ー`等の欠損記号だけの表示を含む。**空欄をクローズ `×` に変換しない。** 「掲載がない」ことと「閉鎖している」ことは別の事実であり、`×` へ潰すと後から区別できなくなる。取得した生値は `note` に残す（空文字なら `note: null`）。

公式が凡例や注記で「空欄＝閉鎖」と明示している場合だけ `×` にしてよい。その場合は根拠となる凡例・文言を報告する。営業中の行と空欄の行が混在していることは根拠にならない。

空欄を理由とする警告は隠さない。`status: null` はそのまま `checkCourse` / `checkLift` へ渡す。

適用前に対象行・名称・状態欄の取得成功を確認する。空欄文字列の判定とDOMの存在確認は分離する。DOM消失、navigation失敗、セレクター不一致、読み込み未完了、行・状態要素の欠落は「空欄」ではなく取得失敗として扱い、警告・診断を残す。空名・重複・件数異常の検証も維持する。

「営業する項目だけを列挙する」一覧全体が空の場合、見出しと一覧コンテナを正常に取得でき、調査範囲内の公式資料・アーカイブ・capability台帳から固定在庫の全名称が確認できれば、その在庫を全件 `status: null` として列挙する。固定在庫が不明なら名前を作らない。固定行を持つ表から行が消えた場合や、一部だけ列挙された一覧の未掲載項目は、このルールで補わない。

このルールは運行・滑走の状態に適用する。天気、積雪、日時、コメント等の空欄も `null` のままとし、0や閉鎖状態に置き換えない。空欄以外の未知状態も `null` と生値の `note` を残し警告する。
## capability台帳

冬季に何が取得できるかを記録した台帳。本番DBの `data_documents` にキー `resorts-temporary/latest_status_capability/<resort-id>.json` で保存する。オフシーズンの実装・監査の基準になるので、冬季アーカイブを調査したら必ず更新する。

台帳が記録するのは「そのスキー場で、営業期間中に公式が掲載する情報」であり、実行時点の値ではない。値は入れない。

```jsonc
{
  "version": 1,
  "resortId": "kamui-ski-links",
  "source": { "mode": "WAYBACK_VALIDATION", "archiveTimestamp": "20250201", "urls": ["..."] },
  "observedAt": "2026-09-18T00:00:00.000Z",
  "crawlerSourceHash": "<そのとき使ったクローラーのsha256>",
  "courses": {
    "available": true,
    "count": 25,
    "fields": { "name": true, "status": true, "update": false, "note": true },
    "names": ["...", "..."],
    "statuses": ["○", "×"]
  },
  "lifts": { "available": true, "count": 6, "fields": {...}, "names": [...], "statuses": [...] },
  "conditions": {
    "comment": true,
    "points": ["山頂", "山麓"],
    "fields": {
      "update": true, "weather": true, "temperature": true,
      "snowDepth": true, "snowfall": false, "condition": false, "windSpeed": false
    }
  }
}
```

- `available: false` は「公式ページにそのカテゴリが存在しない」ことを意味する。調査できていない場合は台帳に書かず、TODOを残す。
- `fields` の `true` は「営業期間中はその項目が埋まる」ことを意味する。冬季アーカイブで1度でも取得できた項目を `true` にする。
- `names` は冬季に列挙されたコース名・リフト名。対応表の初期値と、空の営業項目一覧を補うときの固定在庫の根拠になる。
- `statuses` は冬季に実際に現れた状態記号。未知値の判定基準に使う。
- `crawlerSourceHash` は台帳を作ったときのクローラーファイルのハッシュ。抽出ロジックを変更したら台帳を作り直す。

### 欠損警告

営業期間中の実行で、台帳が `true` としている項目が取得できなかった場合は警告を出す。`CrawlLatestIssue` に `CAPABILITY.MISSING_*` として残し、該当カテゴリの現在値への昇格を止める。台帳が `false` としている項目は、取得できなくても警告しない。

台帳がないスキー場では欠損警告を出さない。警告が出ないこと自体を「正常」と読み替えない。

## データの意味

### comment と newsUrl

`comment` は、当日のコンディション、営業範囲、雪面、全体的な注意など、営業・ゲレンデ情報内の専用コメント欄だけから取得する。ニュース、お知らせ、ブログ、最新記事、一覧へのリンク文は代用しない。個別コース・リフトの可変情報は各 `note` に入れる。専用欄がなければ `comment: null` とする。

`commentUrl` と `newsUrl` は役割が違う。取り違えない。

| フィールド | 意味 | 条件 |
| --- | --- | --- |
| `commentUrl` | `comment` の本文を実際に取得したページ | クローラーがそのページを開き、locatorでコメント本文を抽出している |
| `newsUrl` | お知らせ・ニュース一覧など、利用者が自分で読むための参照リンク | 本文は取得しない。掲載場所を案内するだけ |

- `comment` を取得したページのURLは必ず `commentUrl` に入れる。別ページから取得しておいて `commentUrl` に無関係なURLを並べない。
- 本文を取得していないお知らせ一覧・ブログ・SNSへのリンクは `commentUrl` ではなく `newsUrl` に入れる。
- 両方に同じURLを重複して入れない。専用コメント欄とお知らせ一覧が同一ページにあり、本文を取得している場合は `commentUrl` だけにする。
- どちらも該当がなければ `[]`。
- ニュース一覧は、`newsUrl` に載せる目的だけなら巡回しない。URLを記録するだけでよい。

### update

- トップレベルの `time` は実行時刻、`WeatherData.update`、`Course.update`、`Lift.update` は公式が対応情報に掲載する更新日時。
- 項目固有日時を優先し、なければカテゴリ共通日時を使ってよい。全体日時は全カテゴリ対象と明示される場合だけ使う。
- 別カテゴリの日時、実行時刻、ファイル日時、HTTP日時、Wayback日時で補完しない。公式日時がなければ `null`。
- 日時を伴わない `現在`、`更新`、空欄、`-` は更新日時として扱わない。
- 可視DOMより直接的な埋め込みJSONや `data-*` の項目別日時を使ってよい。採用した生値と適用範囲を報告する。

### 状態

- `status` は `○`、`△`、`×`、または `null`。公式凡例を優先し、凡例がなければ同ページの別表示や営業中アーカイブで意味を確定する。
- 営業中、休止・閉鎖、一部営業、待ち・準備中・見合わせ、未掲載を区別して確認する。
- 一覧の状態要素を主根拠とし、地図など別表示は照合・補助に使う。
- テキスト、class、`data-status`、画像名、`alt` の対応を明示的な純粋関数にする。正常取得した空欄は上記のルールで `null` とし、未知値を開閉どちらかへ寄せない。
- 変換不能な公式状態は `status: null` とし、生値を `note` に残す。変換済みの状態表現は `note` に重複させない。
- `status: null` も `checkCourse` / `checkLift` へ渡し、状態警告が出ることを確認する。

### 名前とnote

```ts
const courseNameMap: Record<string, string[]> = {};
const liftNameMap: Record<string, string[]> = {};
```

- mapは空でも残し、`map[rawName] ?? [rawName]` で1対多を許容する。
- コース名から文字列 `コース`、リフト名から文字列 `リフト` を除く。
- 公式DOMで記号・番号と名称が別要素なら、`A ホーゲル` や `1 パノラマ` のように半角スペース1文字で結合する。英数字で始まるだけの名称を記号と推測しない。
- `note` は当日の利用判断に役立つ可変情報だけにする。固定の紹介、難易度、距離、定型注記、出典ラベルは入れない。
- 積雪は `積雪: 120cm` とし、欠損記号は残さない。例外文言があれば `積雪: 120cm / 整備中` のように追加する。状態記号だけなら `note: null`。
- 圧雪・非圧雪、営業時間、運休理由、利用制限など、その日の可変情報も簡潔に残す。

## 欠損・不安定なカテゴリ

一部フィールドが季節的に空でも、取得できるフィールドを残して該当値だけ `null` にする。正常取得したコース・リフトの状態欄が空欄なら `status: null` とする。検証設定では「構造的に非掲載」と「取得失敗」を区別する。カテゴリ単位では次のように扱う。

| 調査結果 | データ | 対応URL | TODO |
| --- | --- | --- | --- |
| 公式ページにカテゴリがない | 空 | `[]` | 不要 |
| 掲載はあるが安定して対応づけられない | 空 | 参照価値があれば残す | 必要 |
| 安定して取得できる | 実装 | 根拠URL | 不要 |

「不安定」には、日替わりの自由記述・画像告知、実名称ではなく難易度や本数だけなど、項目名と状態を安定して対応づけられない場合を含む。状態欄が空であることやWaybackが利用できないことだけを理由に、現行DOMで名称・状態欄を正常取得できるカテゴリを省略しない。空の営業項目一覧については上記の固定在庫ルールに従い、それ以外では推測した名前やデフォルト状態で補完しない。capability台帳に記録された名称は、固定在庫の根拠として使ってよい。

TODOはimportより前に置き、再調査URL、対象カテゴリ、今回確認できなかった理由、冬季営業中に確認するDOM・名前・状態・件数・更新日時を書く。確認できたカテゴリまでTODOを理由に省略しない。

空データは `weather = {}`、`courses = []`、`lifts = []` とし、対応カテゴリ専用の必須selector・件数検証は呼ばない。カテゴリは独立して扱い、一部カテゴリの非掲載をページ全体の失敗にしない。

## 画像天気

天気を画像URL、`alt`、class、CSS背景、アイコンコードで表す場合は、現在表示中の1種類だけで変換表を作らない。

1. 現在DOMの `src` / `data-src` / `srcset` / `alt` / classと資産prefixを確認する。
2. ページが参照する公式CSS・JavaScript・manifest・同prefixのWayback CDXから兄弟識別子を列挙する。
3. 季節・天候が異なる公式アーカイブで実表示と意味を照合し、可能なら現在URLのHTTP statusとcontent-typeも確認する。

公式ファイル名、`alt`、凡例、公式文言、実アーカイブで意味を確認できた識別子だけを明示的なmapへ入れる。未知識別子、識別子を抽出できない画像、画像URLと`alt`の不一致は、`resortName`、生値、URLを含めて `console.warn` する。URLと`alt`のどちらを主根拠にするか決め、理由をコードコメントに残す。天気欄自体が空のケースは識別子抽出失敗と区別する。未知値は警告後に公式の生値を保持してよいが、既知の天気へ推測変換しない。

検証では既知の全識別子に加え、存在しない識別子とURL・`alt`不一致を変換関数へ通す。調査経路、現在有効か、実DOMで確認できたか、変換値、警告結果を報告する。

## Source URLと保存

- 現行URLの実装検証は `mise run crawl:latest -- --remote-api --resort <resort-id>` を使い、設定済みAPIへの保存とadmin用現在値への反映まで確認する。バッチCLIの既定は `--local-files` なので、現行検証では `--remote-api` を明示する。API保存失敗をローカルJSON保存で代替して完了扱いにしない。
- 冬季アーカイブ・保存DOM再生・異常注入だけはAPI設定を無効化し、現行値と別の `src/private/data/resorts-temporary/tmp/<resort-id>-audit/` を使う。検証JSON・GeoJSON・ログ・補助スクリプト・`--report` 出力もこの配下に置き、親rusutsuの `tmp/` へ出力しない。検証JSONは比較資料であり、現行データのAPI保存とは別の成果物として扱う。

- `weatherUrl`、`commentUrl`、`newsUrl`、`courseUrl`、`liftUrl` は実際の根拠ページへ向ける。入力URLを無条件にコピーしない。
- 利用可能な `#id` やタブのクエリを含め、対象へ直接移動できる最も具体的なURLにする。実在しないフラグメントは作らない。
- URL配列の欠損は `""` ではなく `[]`。カテゴリ非掲載なら空、不安定でも参照価値がある場合だけURLを残す。
- `Utils.saveLatestResult(import.meta.url, ...)` で保存先を絶対化し、親ディレクトリを作る。必須ページ取得失敗時は不完全JSONを最新値として保存しない。
- `Utils.saveLatestResult` は必ず `await` する。`DATA_API_BASE_URL` が設定されている実行では `.env` の `INTERNAL_DATA_API_CRAWLER_TOKEN` を使ってサーバーへ送信し、個別クローラーからローカルの最新JSONを直接書かない。クローラーへ `INTERNAL_DATA_API_ADMIN_TOKEN` を渡してはならない。非loopbackの `DATA_API_BASE_URL` はHTTPS必須で、平文HTTPを許可するのは `localhost`、`127.0.0.1`、`[::1]` だけとする。トークン不足、認証失敗、通信失敗は成功扱いにせず非0で終了する。
- 最終結果は共有検証でも全コース・リフトの名前と状態、重複、source URL、source URLがあるカテゴリの空データを検査する。ただし、共有検証を理由にサイト固有の生値チェックを省略しない。未知の生値は変換時点で警告し、DOMに残るようにする。
- 抽出例外はbrowserが開いている間に `console.error` へ渡して `process.exitCode = 1` を設定し、その後 `finally` でbrowserを閉じる。browser close時に診断保存とremote API送信が完了するため、例外をbrowser close後に初めて記録する構造にしない。
- 取得値の変換表にデフォルトの成功値を置かない。未知値は生値付きで警告し、対応する診断DOMを保存する。
- browserは `finally` で閉じる。調査HTMLは生成物としてGit管理しない。

## 検証チェック

- 現行URLでクローラーをremote-apiモードで実行し、APIのrun・カテゴリ保存結果とadminが参照する現在値を読み戻す。スキー場ID、カテゴリ、名前、状態、件数、URL、`note`、`update`、コメント、警告を根拠DOMと照合する。
- `resortName`、空の名前、重複、想定外件数を確認する。期待件数は固定在庫にだけ使い、季節で増減する項目へ強制しない。
- 正常・無警告で診断DOMが増えないことに加え、未知状態、必須selector消失、空名・重複・件数異常で、警告とDOMが同じ診断実行として残ることをテストする。
- 掲載カテゴリに応じて `checkAllWeatherData`、`checkCourseLiftCount`、`checkUrl` を使い、構造的に存在しないカテゴリの検証だけを省く。
- 公式凡例にある全状態、または取得できた営業中・一部営業・休止中の状態を変換関数へ通す。件数一致だけで成功としない。
