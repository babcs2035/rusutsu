## 新形式の判断

次を満たす実装を基準にする。

- `../shared/type` の `WeatherData`、`Course`、`Lift` を使う。
- `../shared/utils` のnavigation、文字正規化、検証関数を使う。
- `resortName`、各source URL、件数を明示する。
- `path.resolve(baseDir, ...)` と `fs.mkdirSync(..., { recursive: true })` で保存する。

参考例の用途:

- `hakuba-happo-one.ts`: 状態画像がある列の検出
- `kiroro-snow-world.ts`: 同名classを見出しと親要素で限定、前後のテキストノード抽出
- `geto-kogen.ts`: DOM上のIDと画像コードによる安定した対応
- `kagura.ts`: クエリ・フラグメント付きsource URLと非表示タブ内DOM

既存例のデフォルト状態や固定件数をそのまま正解とみなさず、対象サイトで再検証する。

## DOMの調査

- 最終的な抽出環境と同じPlaywright・localeで開く。
- `domcontentloaded` 後、対象要素の `attached` を待つ。
- タブが非表示でもDOMに存在するか確認する。存在するなら不要なクリックを避ける。
- Ajaxで後から追加される場合だけ、クリックやレスポンス待機を加える。
- `page.content()` は必要な操作後に保存する。
- console errorは抽出失敗と無関係な外部広告エラーもあり得るため、内容を確認して判断する。
- 見出しとセクションを一巡し、コメント、天気、気温、積雪、降雪、雪質、風速、更新日時、コース、リフトの掲載有無を実装前に記録する。
- 1つのカテゴリで一部の値だけが空でも、カテゴリ全体を欠損扱いにしない。

## commentの取得元

`comment` は、コンディション、ゲレンデ情報、当日の営業状況などのページ内にある、現在の利用判断に直接役立つ専用コメント欄からだけ取得する。

取得対象の例:

- 当日のゲレンデ・雪面・営業範囲に関する現地コメント
- スキー場全体に関する営業上の注意や案内
- 施設が現在状況として表示するスタッフメッセージ

取得対象外:

- ニュース一覧、お知らせ一覧、ブログ一覧、記事アーカイブの先頭記事・最新タイトル・日付
- 一覧ページへのリンクを案内するために生成したHTMLや定型文
- ページタイトル、最新記事カード、キャンペーン見出しをコメント欄の代わりにしたもの
- 個別コース・リフトの営業時間や運休理由。これらは各項目の `note` に入れる。

ニュース・お知らせ一覧URLは、利用者向け参照先として `commentUrl` に残してよい。`commentUrl` にURLがあることと、`comment` 本文を抽出することは別である。営業・ゲレンデ情報に専用コメント欄がなければ `comment: null` とし、ニュース一覧の内容で補完しない。ニュース一覧は、別の取得目的がない限り `comment` のためだけに巡回しない。

## 更新日時

- トップレベルの `time` はクローラーの実行時刻として扱う。
- `WeatherData.update`、`Course.update`、`Lift.update` は、公式ページが対応する情報について掲載する更新日時として扱う。
- `update` にクローラーの実行時刻、`new Date()`、`now`、`formattedNow`、ローカルファイルの更新日時、HTTPヘッダーの日付、Waybackのキャプチャ日時を入れない。
- 項目固有の更新日時があればそれを優先する。なければ、該当カテゴリの見出し付近にあるカテゴリ共通日時を各項目へ適用してよい。
- 天気の更新日時をコースやリフトへ、リフトの更新日時をコースへ流用しない。ページ全体の日時を使うのは、公式DOM上で全カテゴリに対する更新日時だと確認できる場合だけにする。
- 可視テキストだけでなく、ページが直接埋め込むJSONや`data-*`に項目別の公式更新日時がある場合は利用してよい。可視のカテゴリ共通日時と項目別日時が両方ある場合は、より直接的に該当情報へ対応するものを選び、根拠を報告する。
- 日時を伴わない `現在`、`更新`、空欄、`-` は日時として保存せず `null` にする。
- 対応する公式更新日時が掲載されていないカテゴリ・項目は `null` にする。別の日時やクロール時刻で穴埋めしない。
- 現行DOMと冬季アーカイブDOMの両方で、抽出した`update`が同じセレクターまたは同じページ内データに由来することを検証する。

## 冬季アーカイブ監査

- 現在がオフシーズン、または現在DOMの値・行が空なら、同じ公式URLの直近冬季Waybackスナップショットを必ず確認する。
- 通常は12月から3月、春営業主体なら4月から5月を含め、営業中の実値がある日時を選ぶ。
- 現在コードのセレクターを保存したアーカイブHTMLへ適用し、カテゴリ、名前、状態、件数を機械的に照合する。
- 冬季にだけ現れるカテゴリは現在の空DOMを理由に実装から除外しない。
- 夏季の `-`・空欄・0行を閉鎖へ変換する場合は、冬季の同一要素に状態値またはオープン項目名が入ることと、現在がオフシーズンである根拠を併用する。
- オープン項目だけを列挙する欄では、固定在庫と空欄＝全閉鎖の意味を確認できた場合だけ、空欄時に固定在庫を全件 `×` で補完する。見出し・コンテナの取得成功を先に確認し、DOM消失やセレクター失敗を0件扱いにしない。
- 部分掲載時に未掲載項目も閉鎖扱いできるとは限らない。空欄時の全閉鎖フォールバックとは分けて根拠を確認する。
- アーカイブの営業値を現行値として扱わない。ただしクローラー検証で `latest_data/<resort-id>/` に正常保存されたJSONは、現行結果との比較資料として削除しない。
- Wayback未保存、JS/APIリプレイ不能、リダイレクト失敗は「未確認」として扱う。

## 画像天気の全パターン調査

天気が画像URL、`alt`、class、CSS背景画像、またはアイコンコードで表現されるサイトでは、現在DOMに出ている1種類だけを根拠に変換表を作らない。実装前に次の順で、そのサイトが使い得る識別子を可能な限り列挙する。

1. 保存した現在DOMの `src` / `data-src` / `srcset` / `alt` / classを確認し、ファイル名prefixと公式資産ディレクトリを特定する。
2. ページから直接参照される公式CSS・JavaScript・manifest・テーマ資産を検索する。
3. ディレクトリ一覧が得られない場合は、同じ公式資産URL prefixをWayback CDXで照会し、保存された兄弟資産を列挙する。
4. 季節や天候が異なるコンディションページの公式アーカイブを複数確認し、実際のDOMに出た識別子と意味を照合する。
5. 列挙した公式資産URLが現在も存在するか、HTTP statusとcontent-typeを確認する。アーカイブにしかない識別子は別扱いで記録する。

変換表は公式ファイル名、`alt`、凡例、公式文言、または実アーカイブ表示で意味を確認できたものだけで構成する。画像の見た目や曖昧な略号から意味を推測しない。

未知値の処理は次を満たす。

- `map[token] ?? token` のように無警告で通さない。
- 未知の画像名・`alt`・class・コードを受けたら、`resortName`、生の識別子、画像URLなどを含む `console.warn` を出す。
- 画像URL由来の識別子と`alt`が一致しない場合も警告する。画像URLを主根拠にするか`alt`を主根拠にするかはサイトごとに決め、根拠をコードコメントへ残す。
- 画像要素が存在するのに識別子を抽出できない場合も警告し、天気欄自体が空の場合と区別する。
- WeatherDataの文字列型で表現できる場合は、警告後に公式の未知生値を保持してよい。既知の天気へ推測変換しない。

検証では、列挙した既知識別子をすべて変換関数へ通すほか、存在しないテスト用識別子と、画像URL・`alt`が不一致の組み合わせを通して警告を確認する。最終報告には、全識別子、調査方法、現在有効か、実DOMで確認したか、変換値、未知値警告の結果を含める。

## 壊れにくいセレクター

優先順位の目安:

1. 対象セクションの固有IDや安定した `data-*`
2. 見出しを含む親コンテナ
3. 項目の役割を表すclassや属性
4. 親子関係
5. 固定位置

文字列検索をページ全体へ無差別にかけない。次の用途では文字列を使ってよい。

- 同名classのセクションを見出しで区別する
- 表の列見出しを検出する
- 公式の状態文言を正規化する
- ラベルに対応する値を取得する

例:

```ts
page.locator(
  '.panel-component:has(.panel-tab:has-text("リフト運行状況")) .operation-status-item',
);
```

## 表形式ページ

- 可能なら `th` の正規化済みテキストから列indexを求める。
- 列順が変わっても見出しが同じなら動くようにする。
- 見出しがない、不完全、画像だけなどの場合は固定列フォールバックを使ってよい。
- フォールバックを選んだ根拠をコメントに残す。
- 最初の行だけ構造が異なる可能性を確認する。

## 状態の正規化

状態は最終的に `○`、`△`、`×`、または `null` にする。

- テキストだけでなくclass、`data-status`、画像ファイル名、`alt` を使ってよい。
- 一覧の状態要素を最優先し、地図など別表示は照合・補助に使う。
- 同じ状態の複数表現を明示的に列挙する。
- 未知の画像やclassを開・閉のどちらかへ勝手に倒さない。
- 「状態要素がない」こと自体が公式に特定状態を意味する場合だけ、検証済みフォールバックを使う。
- オープン項目だけを列挙する形式で空欄が全閉鎖を意味する場合は、確認済みの固定在庫を明示し、空欄時だけ全項目を `×` にする。対象欄が見つからない場合は取得失敗とし、このフォールバックを使わない。
- 状態変換は小さな純粋関数に分ける。
- 状態を `null` にした項目も `checkCourse` / `checkLift` で検証し、警告を隠さない。
- 公式の状態文字列を正規化後の `status` とは別に保持する。確実に変換できない文字列は `status: null` とし、生の公式文字列を同じコースまたはリフトの `note` に残す。確実に変換できた既知文字列は `note` に重複して残さなくてよい。
- 公式凡例が状態画像・class・属性の意味を明示している場合は凡例を優先し、凡例に出る各識別子を純粋関数へ通す。
- 公式凡例がなく意味が曖昧な場合だけ、過去アーカイブや同ページ内の別表示で意味を確定する。

## 名前と名寄せmap

```ts
const courseNameMap: Record<string, string[]> = {};
const liftNameMap: Record<string, string[]> = {};
```

- mapは空でも削除しない。
- `map[rawName] ?? [rawName]` で1対多対応を許容する。
- `Course.name` から文字列 `コース`、`Lift.name` から文字列 `リフト` を除外する。DOM・map・別表示のどこから取得した名前でも、配列へ追加する前に同じ規則を適用する。例: `しらかばコース` → `しらかば`、`夢の平クワッドリフト` → `夢の平クワッド`。
- 記号・番号を名前に含めるかは、公式DOMと既存データの両方を確認する。
- 公式DOMでコース記号・番号と本体名が別要素または別ラベルとして並ぶ場合は、できるだけ別々に抽出し、`${code} ${name}` の形で半角スペース1文字を挟む。例: `<span>A</span>ホーゲル` → `A ホーゲル`、番号要素と `パノラマ` → `1 パノラマ`。
- `textContent` が記号・番号と名称を空白なしで連結する場合も、DOM上で両者が別要素だと確認したうえで半角スペースを補う。通常名称が英数字で始まるだけの場合は、記号・番号だと推測して空白を挿入しない。
- 装飾用spanを除く場合は、テキストノード抽出または記号・番号spanの値を先頭から除く。
- 空白、全角英数字、不要な接尾辞だけを根拠を持って正規化する。

## note

- その日の可変情報だけを入れ、一般的なコース紹介文、地形説明、難易度、距離、毎日同じ注記、推測方法の説明は入れない。
- `公式表示:`・`備考:` のような出典ラベルを機械的に付けず、利用者に必要な値や文言を直接記載する。
- コース行に積雪値があれば、`積雪: 120cm` の形式で残す。積雪が `-`・`ー`・空欄なら残さない。
- `○`・`〇`・`◯`・`◉`・`△`・`×`・`✕`・`-`・`ー` など、正規化済みの `status` と同じ意味しか持たない記号は `note` に重複させない。
- 状態記号と積雪値を取り除いた後に `整備中`・`人工降雪作業中`・運休理由・利用制限など、その日に固有の公式文言が残る場合だけ、その文言を接頭辞なしで追加する。
- 例: `◉ 120cm` は `積雪: 120cm`、`整備中 120cm` は `積雪: 120cm / 整備中`、`人工降雪作業中` は `人工降雪作業中`、`ー ー cm` は `null` にする。
- 圧雪・非圧雪、営業時間、運休理由、利用制限など、現在の利用判断に役立つ他の可変情報も簡潔に残す。
- 値だけで意味が明確な `圧雪`・`非圧雪` には `圧雪状況:` のようなラベルを付けない。
- 状態文字列を `○`・`△`・`×` に確実に変換できない場合は、推測せず `status: null` とし、その公式文字列を `note` に残す。コースとリフトの両方へ適用する。
- 確実に変換できた既知の状態文字列は、利用者向けに別途必要でなければ `note` に重複して残さない。

## 欠損カテゴリ

公式ページにカテゴリがないことを保存HTMLの棚卸しで確認した場合:

- `weather = {}`
- `courses = []`
- `lifts = []`
- 対応URLは `[]`
- そのカテゴリの必須selector、件数検証、空データ検証を実行しない

一部カテゴリがないことをページ取得全体の失敗にしない。必要なURLごとに成功条件を定義する。

公式ページにカテゴリがある場合は、現在値が空欄でも取得可能な他フィールドを実装する。季節的な空欄はそのフィールドを `null` にし、検証設定で「構造的に存在しない値」と「取得失敗」を区別する。カテゴリを空にする理由は完了報告へ記載する。

コース・リフトカテゴリが存在し、オープン項目だけを列挙する仕様と空欄時全閉鎖を確認済みなら、空配列にはしない。確認済みの固定在庫を全件 `×` で出力する。

## URL

- JSON内のURLは抽出に使った根拠ページへ向ける。
- `#id` があるなら、その箇所へ直接移動できるか確認する。
- タブ指定が必要なら `?tab=lift#menu03` のようにする。
- 1ページに複数カテゴリがあっても、カテゴリ別に最も直接的なURLを持たせる。
- JavaScriptだけで切り替わりURL表現がない場合は、最も近い安定したセクションIDを使う。

## 保存と失敗処理

- `baseDir = path.dirname(fileURLToPath(import.meta.url))` を使う。
- JSON保存前に親ディレクトリを作る。
- 一部の必須ページ取得が失敗したときは不完全JSONを最新値として保存しない。
- 現行ページまたはWaybackで正常終了して保存されたJSONは検証資料として残す。両方が成功した場合は両方を残し、失敗実行が生成した不完全JSONだけを削除対象にする。
- `try/finally` でbrowserを閉じる。
- 調査HTMLは `crawl_latest_dom/<resort-id>` に保存し、生成物としてGit管理しない。

## 検証

- 現在ページに対して実行する。
- 公式凡例がある場合は凡例に記載された全状態の識別子を状態変換関数で照合する。
- 公式凡例がなく意味が曖昧な場合は、可能なら保存した営業中・一部営業・休止中の過去HTMLで状態変換を照合する。
- 期待件数は固定在庫だけに使う。季節で増減するパーク等には固定件数を強制しない。
- 空欄時全閉鎖フォールバックは、営業中アーカイブでオープン項目、営業終了・定休日等の表示で固定在庫全件の `×` を同じクローラー経路へ通して検証する。
- 名前と状態の両方を確認する。件数一致だけで成功としない。
- 変換不能な公式状態文字列が `note` に残り、既知の状態文字列が不要に重複していないことを確認する。固定のコース説明・推測方法・`公式表示:` が混入せず、積雪と例外文言だけが所定形式で残ることも確認する。
- `update` は天気・コース・リフトごとに公式DOMの根拠と照合し、クロール実行時刻や別カテゴリの日時が混入していないことを確認する。
- `comment` が非nullなら営業・ゲレンデ情報内の専用コメント欄が根拠であることを確認する。ニュース・お知らせ・ブログ一覧の先頭項目やリンク文が混入していないことを確認する。
- `status: null` の件数と状態警告の件数を照合する。`null` を条件に検証をスキップしない。
- 画像天気は調査した全識別子の変換結果を確認し、未知識別子と画像URL・`alt`不一致で `console.warn` が出ることもテストする。
- URLのクエリとフラグメントが出力JSONに残っていることを確認する。
- 完了時に、状態ごとの証拠、テスト済み／未確認、全カテゴリ・フィールドの取得／未取得理由をChatへ報告する。
- オフシーズン監査では、冬季スナップショット日時、対象URL、カテゴリ別件数、現在セレクターの適合結果を報告する。
