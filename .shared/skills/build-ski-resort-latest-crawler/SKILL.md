# Build Ski Resort Latest Crawler

指定された公式URLと、リポジトリ内の新形式を根拠にサイト固有のクローラーを完成させる。

## 必須入力

- スキー場ID
- 調査対象の公式URL

URLが不足して実装対象を特定できない場合だけユーザーに確認する。別のスキー場や公式URLを探索しない。同じURLの過去アーカイブや、ページから直接読み込まれるデータは状態表現の確認に利用してよい。

## 先に読むもの

1. リポジトリの `AGENTS.md`
2. `src/private/scripts/crawl_latest/resorts/template.ts`
3. `src/private/scripts/crawl_latest/shared/type.ts`
4. `src/private/scripts/crawl_latest/shared/utils.ts`
5. `shared` をimportしている完成度の高い既存クローラーを複数
6. [implementation-guidelines.md](references/implementation-guidelines.md)

`shared` を使わない旧形式は設計の基準にしない。既存ファイルも未完成の場合があるため、空のURL・セレクター・resortNameやコメントアウトされた保存処理がないか確認してから参考にする。

## ワークフロー

### 1. レンダリング後DOMを保存する

実装前に、必ずPlaywrightで各URLを実際に開く。必要なタブ切替・クリック・待機を終えた状態でDOMを調査する。

単純なページでは同梱スクリプトを使う。

```bash
node .shared/skills/build-ski-resort-latest-crawler/scripts/capture-rendered-pages.mjs \
  --out src/private/data/resorts-temporary/crawl_latest_dom/<resort-id> \
  --url '<official-url>' \
  --wait-for '<required-selector>'
```

複数URLでは `--url` を繰り返す。保存する調査資料は次だけにする。

- `page.content()` によるレンダリング後の完全HTML
- `console` の error メッセージ

スクリーンショット、抽出対象のDOM断片、可視テキスト一覧、ネットワーク一覧は保存しない。クリック後に初めてDOMへ追加されるサイトでは、同じ保存内容になる最小限のサイト固有Playwright処理を使う。

### 2. 取得可能な情報を棚卸しする

コードを書く前に、保存HTMLの見出しと対象セクションを確認し、次のカテゴリをそれぞれ「掲載あり」「掲載なし」「掲載はあるが値なし」に分類する。

- 営業・ゲレンデ情報ページ内の現在状況コメント
- 天気
- 気温
- 積雪量（地点別を含む）
- 降雪量
- 雪質・コンディション
- 風速
- 更新日時
- コース
- リフト

提供された公式URLに掲載され、既存の出力型で表現できる情報は原則として取得する。「取得可能なカテゴリだけを実装する」は、公式ページにないカテゴリを捏造しないという意味であり、掲載されているカテゴリを任意に省略してよいという意味ではない。

カテゴリやフィールドを空にする場合は、DOM上に存在しない、現在値が `－`・空欄である、既存型では意味を損なわず表現できない、のいずれかを確認し、完了報告に理由を残す。季節により値が空になるフィールドはカテゴリ全体を捨てず、取得できるフィールドを残して該当値だけ `null` にする。

トップレベルの `time` と各データの `update` を混同しない。`time` はクローラーの実行時刻、`WeatherData.update`・`Course.update`・`Lift.update` は公式ページがその情報について掲載している更新日時である。`update` に `new Date()`、`now`、`formattedNow`、ファイル更新日時、Waybackの保存日時を入れない。天気・コース・リフトごと、可能なら項目ごとに対応する公式更新日時を取得し、対応日時が掲載されていなければ `null` にする。詳しい優先順位と禁止事項は [implementation-guidelines.md](references/implementation-guidelines.md) の「更新日時」を参照する。

### 3. commentは現在の営業情報にあるコメント欄だけから取得する

`comment` は、コンディション、ゲレンデ情報、当日の営業状況などのページ内に施設が設けた、現在の利用判断に直接役立つコメント・メッセージだけを対象にする。たとえば当日のゲレンデ状況、雪面状況、営業範囲、運行への全体的な注意、現地スタッフコメントなどである。

- ニュース一覧、お知らせ一覧、ブログ一覧、記事アーカイブの先頭記事や最新タイトル・日付を `comment` に代用しない。
- ニュース一覧等へのリンク文をHTMLで生成して `comment` に入れない。URLが利用者向けに有用なら `commentUrl` に追加するだけでよい。
- ニュース一覧ページは、ユーザーが別カテゴリの取得元として明示した場合を除き、`comment` 抽出のためだけには巡回しない。
- 営業・ゲレンデ情報ページ内に専用コメント欄がなければ `comment` は `null` にする。ニュースの見出しで穴埋めしない。
- 個別コース・リフトの営業時間、運休理由、注意書きは原則として各項目の `note` に入れ、全体の `comment` と混同しない。
- `commentUrl` にURLがあっても、必ず `comment` 本文を取得するという意味ではない。本文の取得可否と参照URLの有無を分けて扱う。

### 4. オフシーズンなら冬季公式アーカイブを必ず確認する

現在がオフシーズン、または現在ページのカテゴリ・値・行が空の場合は、実装前に同じ公式URLのWayback Machineを確認する。現在DOMだけを根拠に「カテゴリなし」と判断しない。

- 原則として直近シーズンの12月から3月を調べ、営業中の値が掲載されたスナップショットを最低1件保存する。
- 春営業が中心のスキー場は4月から5月も調べる。
- トップ、天気、コース、リフト等が別URLなら、各URLを個別に調べる。
- アーカイブURLもPlaywrightで開き、必要な待機後の完全HTMLとconsole errorだけを `crawl_latest_dom/<resort-id>/archive-<timestamp>/` へ保存する。
- アーカイブ上で、コメント、天気、気温、積雪、降雪、雪質、風速、更新日時、コース、リフトを再度棚卸しする。
- 現在のセレクターをアーカイブDOMへ実際に適用し、名前・状態・件数を抽出できるか確認する。目視だけで「冬なら取れる」と判定しない。
- Waybackのツールバーやリプレイ用要素を公式DOMと誤認しない。アーカイブ値は現行値として扱わない。ただし検証実行が `latest_data/<resort-id>/` に正常保存したJSONは、ユーザーが現行結果とアーカイブ結果を比較できる判断資料として削除しない。
- スナップショットがない、リプレイ不能、必要なJS/APIが保存されていない場合は、未確認として報告する。推測で合格扱いにしない。

夏季の `-`、空欄、行なしを `×` にするのは、冬季アーカイブで同じ場所に状態値が入るなど、オフシーズンの表示が明示的に閉鎖を意味すると確認できた場合に限る。確認できたサイトでは、そのフォールバックをコードコメントと監査報告に残す。

公式欄が「当日オープンする項目だけ」を列挙する形式では、次のすべてを満たす場合に限り、欄の `-`・空欄・0件を「確認済みの固定在庫がすべてクローズ」と解釈し、全項目を `status: "×"` で出力する。

- コース・リフト欄の見出しとコンテナ自体は正常に取得できている。
- 全コース・全リフトの固定在庫名を、公式の静的案内、営業中アーカイブ、またはユーザー指定で確認している。
- 空欄が全閉鎖を意味することを、公式の営業終了・定休日表示、冬季アーカイブ、またはユーザー指定で確認している。

対象コンテナの消失、ナビゲーション失敗、セレクター不一致を全閉鎖へ変換しない。部分的に名前が掲載された場合、未掲載項目まで `×` にするかは別途根拠を確認し、空欄時のフォールバックを流用しない。

### 5. 画像で表現された天気は全パターンを調査する

天気がテキストではなく、画像URL、`alt`、class、CSS背景画像、アイコンコードのいずれかで表現されている場合は、現在表示中の1種類だけで実装しない。状態変換を書く前に、その公式サイトが使い得る天気識別子を可能な限り全件調査する。

- まず保存した現在DOMから、天気画像の `src` / `data-src` / `srcset` / `alt`、class、ファイル名の共通prefix、格納ディレクトリを確認する。
- ページから直接参照される公式CSS・JavaScript・manifest・テーマ資産、または同じ公式資産URL prefixに対するWayback CDXを使い、兄弟アイコンや識別子を列挙する。これは指定URLから直接読み込まれるデータの調査であり、別スキー場や別サイトのURL探索には広げない。
- 現在と季節・天候が異なる公式ページのアーカイブも確認し、実際にDOMへ出たファイル名・`alt`・classと意味を照合する。
- 列挙した候補は、可能なら現在の公式URLでHTTP statusとcontent-typeを確認する。現在は消えていてアーカイブだけに存在するものは、その旨を区別する。
- 変換表には、公式資産名、公式`alt`、公式文言、実アーカイブ表示などで意味を確認できた識別子だけを入れる。曖昧な略号や画像内容を推測して変換しない。
- 既知の全識別子を明示的な変換表へ通す。将来、変換表にない画像名・`alt`・class・コード、または画像URLと`alt`の不一致が来た場合は、`resortName`、未知の生値、画像URLなど原因を追える情報を `console.warn` に必ず残す。
- `map[token] ?? token` のように未知値を無警告で通さない。天気の型が文字列を許す場合は警告後に公式の生値を保持してよいが、既知の天気へ勝手に寄せない。
- 画像があるのに識別子を抽出できない場合も警告する。天気欄そのものが空であるケースとは区別する。

### 6. 状態の意味を確認する

現在ページに公式の凡例があり、状態画像・class・属性と意味の対応が明示されている場合は、その凡例を一次根拠にしてよい。凡例の各識別子を状態変換関数へ通して検証し、意味の確認だけを目的とする過去アーカイブ調査は必須としない。

凡例や明示的な説明がなく、現在表示だけでは意味が確定できない場合は、同じ公式URLの過去アーカイブなどから、次を可能な範囲で確認する。

- 営業中
- 営業休止・クローズ
- 一部営業
- 運行待ち・準備中・見合わせ
- 項目や状態が未掲載

過去HTMLは状態表現を理解する証拠として使い、最新値として出力しない。確認できなかった状態を推測だけでマッピングしない。

### 7. 抽出設計を決める

取得可能なカテゴリだけを実装する。コースのみ、リフトのみ、天気のみなどを正常な入力として扱い、全カテゴリが存在する前提を置かない。

セレクターと状態判定は保存HTMLで根拠を確認する。見出し、親セクション、ID、class、属性、画像の `src` / `alt`、DOM上の位置関係を組み合わせてよい。必要ならPlaywrightの `:has()` / `:has-text()` を使い、同名classを対象セクションへ絞り込む。

### 8. 実装する

- `src/private/scripts/crawl_latest/resorts/<resort-id>.ts` に追加する。
- `crawl_latest/shared` の型と関数を使う。
- `courseNameMap` と `liftNameMap` は空でも必ず残す。
- 出力するコース名から文字列 `コース`、リフト名から文字列 `リフト` を除外する。たとえば `しらかばコース` は `しらかば`、`夢の平クワッドリフト` は `夢の平クワッド` とする。
- 公式DOMでコース記号・番号と名称が別要素または別ラベルとして並ぶ場合は、記号・番号を残し、名称との間を半角スペース1文字で結合する。たとえば `<span>A</span>ホーゲル` は `A ホーゲル` とする。
- 不明な状態を根拠なく `○` や `×` にしない。型が許す場合は `null` にし、変換できなかった公式の状態文字列をその項目の `note` に残す。確実に変換できた既知文字列は `note` に重複して残さなくてよい。コースとリフトの両方へ同じ規則を適用する。
- オープン項目だけを列挙する欄で、確認済みの空欄時全閉鎖フォールバックを使う場合は、固定在庫を明示し、全項目を `checkCourse` / `checkLift` へ渡す。コンテナ取得失敗と0件を同じ条件にしない。
- 画像天気の変換では全件調査した明示的なmapを使い、未知識別子と画像URL・`alt`不一致を `console.warn` へ残す。
- `comment` は営業・ゲレンデ情報内の専用コメント欄だけから取得し、ニュース・お知らせ・ブログ一覧の先頭項目やリンク文で代用しない。専用欄がなければ `null` にする。
- 配列へ追加する全コース・リフトを `checkCourse` / `checkLift` へ渡す。`status === null` を理由に検証呼び出しを省略して警告を隠さない。
- `update` には、その天気・コース・リフトに対応して公式ページが掲載する更新日時だけを入れる。カテゴリ共通日時は該当カテゴリの全項目へ使用してよい。別カテゴリの日時やクロール実行時刻で補完せず、掲載がなければ `null` にする。
- `note` にはその日の可変情報だけを入れ、一般的なコース紹介文・地形説明・毎日同じ注記・`公式表示:` のような出典ラベルを入れない。コース行に積雪値があれば `積雪: 120cm` の形式で残す。`○`・`〇`・`◯`・`◉`・`△`・`×`・`✕`・`-`・`ー` など、`status` で表現済みの記号だけは重複させない。記号と積雪を除いた後に `整備中`・`人工降雪作業中`・運休理由・利用制限などの例外的な公式文言が残る場合だけ、その文言を接頭辞なしで追加する。例: `◉ 120cm` → `積雪: 120cm`、`整備中 120cm` → `積雪: 120cm / 整備中`、`ー ー cm` → `null`。圧雪・非圧雪、営業時間など当日の利用判断に必要な他の可変情報も簡潔に残す。
- 出力先は `import.meta.url` を基準に絶対化し、保存先ディレクトリを作成する。
- `browser.close()` を `finally` で保証する。

存在しないカテゴリは空のオブジェクトまたは配列で出力し、そのカテゴリ専用の検証を呼ばない。URL配列には欠損を表す `""` を入れず、空配列を使う。

### 9. source URLを利用者向けに整える

`weatherUrl`、`commentUrl`、`courseUrl`、`liftUrl` は、可能ならページ内の対象箇所へ直接移動できるURLにする。

- 対象セクションにIDがあれば `#id` を付ける。
- タブをクエリで指定できる場合は、クエリとフラグメントの両方を残す。
- 例: `...?tab=lift#menu03`
- コースとリフトが同じページでも、直接表示できるタブが異なるなら別URLにする。
- 根拠のないフラグメントを作らず、実際に遷移できることを確認する。

### 10. 検証する

1. クローラーを実行する。
2. JSONが正しいスキー場IDのディレクトリへ保存されたことを確認する。
3. 名前、状態、件数、URL、`note`、`update` を確認する。
   コース記号・番号が名称と並ぶ場合は、出力名が半角スペース1文字で区切られていることも確認する。
   `status` に変換できない公式状態文字列が `note` に残り、変換済みの既知文字列が不要に重複していないことも確認する。固定のコース説明や `公式表示:` が混入せず、積雪が `積雪: <値>cm`、例外文言が接頭辞なしで出力されることも確認する。
   `update` が公式DOMの対応要素またはページ内データと一致すること、トップレベルの `time` や実行時刻を複製していないことも確認する。
4. 空文字の名前・不明な状態・重複・想定外件数を確認する。
5. 対象ファイルをBiomeで検査する。
6. `mise run typecheck` を実行する。

現行ページまたはWaybackに対するクローラー実行が成功し、`latest_data/<resort-id>/` にJSONを保存した場合、その出力は検証資料としてそのまま残す。途中の失敗実行が不完全JSONを生成した場合だけ削除してよい。現行とWaybackの両方が成功した場合は両方のJSONを残し、完了報告で各ファイルがどちらの実行結果か区別する。

`comment` が非nullの場合は、営業・ゲレンデ情報ページ内の専用コメント欄から取得したことを確認する。ニュース・お知らせ・ブログ一覧の先頭記事や、一覧へのリンク文が混入していないことを確認する。専用コメント欄がない場合は、`comment: null` と参照用の `commentUrl` が両立してよい。

画像天気を使う場合は、調査で見つけた全識別子を変換関数へ通し、期待する天気へ変換されることを確認する。加えて、存在しないテスト用識別子を1件通し、`console.warn` が実際に出ること、既知の天気へ誤変換されないことを確認する。画像URLと`alt`の両方を使う実装では、不一致時の警告も確認する。

現在がオフシーズンの場合は、保存した冬季アーカイブHTMLに対しても抽出経路または同じセレクターの検証処理を実行し、冬季のカテゴリ別件数と状態別件数を記録する。

空欄時に固定在庫をすべて `×` にする実装では、営業中表示でオープン項目が `○` になることに加え、営業終了・定休日等の空欄表示で固定在庫の全件が `×` になることを同じクローラー経路で検証する。固定在庫の名前、件数、根拠を記録する。

既存クローラーは `CRAWL_LATEST_ARCHIVE_TIMESTAMP=YYYYMMDD` を付けて実行すると、`navigateSafely` を通る公式URLを同日時のWaybackスナップショットへ切り替えられる。この方法で本番と同じ抽出経路を検証し、Wayback側の最寄りスナップショットへ移動した場合は最終URLの日時も記録する。直接 `page.goto` する特殊実装では、同等のアーカイブURLを明示して検証する。

サイトが現在表示していないカテゴリや状態については、その事実を結果と報告に明記する。警告を消すためだけの推測値や無条件フォールバックは追加しない。

出力に `status: null` が1件でもある場合、状態検証の警告が出ることを確認する。`null` があるのに警告ゼロなら検証を迂回していないか調べる。「警告なし」を完了条件にするために、検証を条件分岐でスキップしてはならない。

### 11. Chatへ状態・取得範囲の監査結果を報告する

skillの実行を終えるたびに、最終回答へ必ず「状態・取得範囲の監査」を含める。ユーザーが再調査の要否を判断できる具体性で、次を記載する。

- コースとリフトについて、`○`・`△`・`×`・待ち／準備中など各状態を確認できたか
- 空欄時に固定在庫を全件 `×` とした場合は、空欄＝全閉鎖の根拠、固定在庫名、全件数、コンテナ取得成功の確認方法
- 根拠が現在の実表示、公式凡例、公式アーカイブのどれか。アーカイブなら対象日時
- 確認した画像名、class、属性、公式文言と、変換後の値
- 状態変換関数またはクローラー経路へ実際に通してテストしたか
- 確認できず `null` にした状態、推測していない点、残るリスク
- 天気・気温・積雪・降雪・雪質・風速・コメントの取得／未取得と、その理由
- 天気・コース・リフトの各 `update` について、根拠要素・公式生値・適用範囲を記載する。未取得なら、対応する公式更新日時が掲載されておらず `null` とした旨を記載する
- `comment` を取得した場合は営業・ゲレンデ情報内の根拠要素、未取得の場合は専用コメント欄がなかったこと。ニュース一覧を代用していないことと、参照URLだけを `commentUrl` に残した場合はその旨
- 画像天気を使う場合は、調査した全識別子、調査経路、現在URLでの存在確認、実DOM・アーカイブで確認できた種類、変換後の値、未知値警告のテスト結果
- 現在ページの実行結果、件数、警告の有無
- 冬季アーカイブの対象日時とURL、カテゴリ別件数、同じセレクターで抽出できたか
- `latest_data/<resort-id>/` に残した現行・Wayback検証JSONのファイルパス

「確認済み」とだけ書かない。たとえば「openのclassは確認できず、地図の `data-status=open` のみ確認した」「雪の天気アイコンは現在ページにも凡例にもなく未確認」のように、ユーザーが追加でアーカイブを探す必要がある箇所を明示する。
