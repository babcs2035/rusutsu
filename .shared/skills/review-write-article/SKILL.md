# スキー場レビュー記事JSONの作成

`src/private/data/reviews/<resortId>/detail.json` だけを根拠に、同じディレクトリの
`article.json` を作成する。

対象カテゴリは次の7つに固定する。

`beginner` / `intermediate` / `advanced` / `moguls` / `powder` /
`tree-run` / `park`

作業前に次の資料をすべて読む。

- [references/review-json-format.md](references/review-json-format.md)
- [references/article-format.md](references/article-format.md)

## 役割

`detail.json` に書かれた調査結果を、初めて行く人が読める日本語に直す。

調査者の分類や判定過程を短く要約する仕事ではない。読み手が知りたいのは、実際にどんな斜面が
いくつあり、どれくらい続き、どこで困るかである。記事を読んだ人がゲレンデの様子を思い浮かべ、
ほかのスキー場と比べられる状態を目指す。

| 項目 | 作業 |
| --- | --- |
| `score` | `detail.json` からそのままコピーする |
| `full` | 来場判断に最も影響する事実を3〜5件書く |
| `reason` | 各カテゴリで知っておくべき事実を2〜5件書く |
| `courses` | `detail.json` にあるコースだけを自然な日本語で説明する |
| `warn` / `warnReason` | `detail.json` からそのままコピーする |

## 読み手

日本のスキー場へ初めて行くスキーヤー、スノーボーダーを想定する。圧雪、非圧雪、コブ、パーク
など一般的なゲレンデ用語は使ってよい。調査・採点・データ整理の用語を知っている前提にはしない。

## 文章を作る順序

### 1. 先に事実を一つずつ取り出す

各カテゴリの `detail.json` から、来場判断に効く事実だけをメモする。メモには次の3点を入れる。

1. 何の話か: 斜面、コース、リフト、コブ、雪、パークなど
2. どんな事実か: 一つだけ、複数ある、長い、短い、狭い、午後まで残るなど
3. 読者に何が起こるか: 移動が必要、混雑する、別の斜面へ行けるなど

調査の件数、採点理由、証拠の探し方はメモに入れない。

### 2. 事実を主語にして書く

原則として、斜面、コース、リフト、雪など、目で見えるものを主語にする。述語は、そのものが
どうなっているかを直接表す。

- 悪い: 「圧雪急斜面の主力は一系統です。」
- 良い: 「圧雪された急斜面は一つだけです。」
- 悪い: 「初級斜面から山頂迂回へ段階的に進めます。」
- 良い: 「麓には幅の広い緩斜面があります。」
- 良い: 「山頂から下る初級者は迂回コースを通ります。」
- 悪い: 「混雑時の代替周回があります。」
- 良い: 「混んだら隣のリフトへ移れます。」

悪い例の問題は、特定の単語そのものではない。書き手の分析を名詞で圧縮し、読み手に意味の復元を
任せている点にある。単語を別の抽象語へ置き換えず、文全体を事実から書き直す。

### 3. 一文では一つだけ伝える

一つの `text` には一つの事実だけを書く。原因と結果を一緒にしないと意味が通らない場合だけ、
一文の中でつなぐ。

- 良い: 「山頂側の初級コースは幅が狭く、速い人も通ります。」
- 悪い: 「初級コースは長く、混雑もあり、雪質も変わります。」

三つ以上の特徴を並べない。別の判断材料なら項目を分ける。

### 4. 読者が使う言葉へ戻す

調査中に使った分類語を記事へ持ち込まない。次のような意味を言いたい場合は、右側のように事実を
直接書く。

| 書き手の頭の中 | 記事で書くこと |
| --- | --- |
| 一つに集まっている | 「圧雪中斜面は一つだけです」 |
| ほかの選択肢がある | 「混んだら隣の斜面へ移れます」 |
| 繰り返しやすい | 「同じリフトで何度も滑れます」 |
| 情報が弱い | `warn: true` の場合だけ、何が分からないかを具体的に書く |
| 条件によって変わる | 「降雪後は非圧雪になります」のように条件と変化を書く |

## 掲載する情報

次のどれかが分かる事実だけを残す。

- コースや斜面が一つだけか、複数あるか
- 長く続くか、短いか、山頂から麓までつながるか
- 同じリフトで続けて滑れるか、別の場所へ移る必要があるか
- 圧雪、非圧雪、コブ造成、パーク営業が日や時期によって変わるか
- 歩き、スケーティング、乗り継ぎ、受付が必要か
- 朝に混むか、午後まで雪が残るか
- 混雑や閉鎖時に使える別の斜面があるか

次の内容は削る。

- 「カービングできます」「高速ターンを楽しめます」など、カテゴリ名から分かること
- 「人気です」「評価されています」など、評判を事実の代わりにした文
- スキー場の設備を並べただけの文
- 調査件数や証拠の少なさを説明する文。ただし `warn: true` で来場判断に必要な不確かさは除く
- scoreを言い直しただけの文
- ほかの項目や `courses` と同じ内容
- 読み手が意味を推測しなければならない抽象的な文

## 日本語の確認

書いた後、各 `text` とコース説明を一文ずつ次の順で確認する。validatorに通るだけでは不十分である。

1. **意味**: 初めて読む人が、一度で意味を説明できるか。
2. **具体性**: 何が、どこで、どうなるかが書かれているか。
3. **一文一義**: 一文に別々の事実を詰め込んでいないか。
4. **係り受け**: 主語と述語、修飾語と修飾先が離れていないか。
5. **語順**: 条件、場所、対象、動作の順が自然か。
6. **音読**: 同行者へ口頭で説明しても不自然でないか。
7. **情景**: 読後に、斜面の数、長さ、場所、移動のどれかを思い浮かべられるか。

一つでも通らなければ、単語を直すのではなく、`detail.json` の事実へ戻って文全体を書き直す。

## JSONの作成

1. `detail.json` の `resortId` と7カテゴリの必須項目を確認する。
2. 各カテゴリの事実を上記の手順で取り出す。
3. `reason` を2〜5件書く。`○`では、できることと制約を両方残す。
4. 全カテゴリから重要な事実だけを選び、`full` を3〜5件書く。
5. `courses` には `detail.json` のコースだけを残す。コース名は `full` と `reason` に書かない。
6. `score`、`warn`、`warnReason` をそのままコピーする。
7. 既存の `article.json` は根拠として使わず、`detail.json` から書き直す。
8. validatorを実行する。
9. JSONを画面に表示される順で読み直し、上記の日本語確認を行う。

```bash
node .shared/skills/review-write-article/scripts/validate-review-json.mjs \
  src/private/data/reviews/<resortId>/detail.json \
  src/private/data/reviews/<resortId>/article.json
```

article側の警告は0件にする。detail側の警告・エラーはこのskillで直さず、別に報告する。

## 変更してはいけないこと

- `detail.json` にない情報を追加しない。外部を調べない。
- `score` を変えない。
- `warn` と `warnReason` を書き換えない。
- `full` と `reason` にコース名を書かない。
- 数値、年号、媒体名、URL、引用文を記事本文に出さない。
- `label` に `good` / `bad` / `description` 以外を使わない。
- カテゴリを省略しない。`score` に `null` を使わない。

## 完了報告

- 作成した `article.json` のパス
- 7カテゴリの `score`
- `warn: true` のカテゴリと `warnReason`
- article側のvalidator警告が0件になったこと
- detail側に入力警告・エラーがある場合は、その件数と内容
