# スキー場レビュー記事JSONの作成

`src/private/data/reviews/<resortId>/detail.json` だけを根拠に、同じディレクトリの
`article.json` を作成する。

対象カテゴリは次の7つに固定する。

`beginner` / `intermediate` / `advanced` / `moguls` / `powder` /
`tree-run` / `park`

作業前に [references/article-format.md](references/article-format.md) を読む。完成形の見本が
載っている。JSONのキーと必須条件は
[references/review-json-format.md](references/review-json-format.md) にある。

## 目指す文章

これが目標である。ここから外れたら書き直す。

> **良い点**
>
> - 山麓側に幅広く緩やかな独立したコースがあり、初めて板を履く段階から安心して繰り返し練習できます。
> - 滑れるようになった後は、中腹の距離と斜度が少し増す初中級斜面へ進めるため、段階的に上達できます。
> - 雪遊び用の区画と動く歩道もあります。
>
> **気になる点**
>
> - 駐車場やシャトルバスの降車地点からアクセスリフトまで、坂道を含む徒歩と用具運搬が必要で、子ども連れや初心者には負担になる場合があります。
> - 休日は山麓の初心者用斜面とリフトが混みやすく、離れたエリアへ移る際にも体力を使います。
>
> **代表的なコース**
>
> - 豪円山エリア：幅広く凹凸の少ない緩斜面で、初滑りや家族での繰り返し練習に適しています。
> - 中の原エリア：下部は初心者も利用しやすく、豪円山から次の段階へ進む際に使えます。
> - U1コース：幅に余裕のある初中級斜面で、ターンを覚えた後に少し難しい斜面へ進む際に向いています。
> - タカぴよランド：動く歩道があり、そりや雪遊びを楽しむ小さな子どもに便利です。

「良い点」「気になる点」が `reason`（`label` は `good` / `bad`）、「代表的なコース」が
`courses` にあたる。

## 文の形

箇条書きの1項目は、次の2つをつないだ1文にする。

```
[ゲレンデで見える事実] + [それが読み手にとって何を意味するか]
```

- 「山麓側に幅広く緩やかな独立したコースがあり」＋「初めて板を履く段階から安心して繰り返し練習できます」
- 「坂道を含む徒歩と用具運搬が必要で」＋「子ども連れや初心者には負担になる場合があります」
- 「休日は山麓の初心者用斜面とリフトが混みやすく」＋「離れたエリアへ移る際にも体力を使います」

**事実だけを置いて終わらせない。** 「幅が広いです」「コブがあります」「移動が多くなります」で
止めると、読み手は自分に関係があるかを自分で考えることになる。誰が、どの段階で、何をするときに
効いてくるのかまで書く。

後半の「意味」も `detail.json` から取る。`detail.json` には「初心者の練習向き」「負担」
「滑る範囲が狭まりやすい」のように、すでに意味まで書かれていることが多い。想像で足さない。

短い事実がそれだけで完結するなら、無理に後半を付けなくてよい。

- 「雪遊び用の区画と動く歩道もあります。」

## 使ってよい言葉

前の版で禁止していたが、上の見本で使われている。禁止しない。

- 位置を表す言葉: 山麓側、中腹、上部、下部、山頂側、離れたエリア
- 段階を表す言葉: 初中級斜面、段階的に上達、次の段階へ進む、ターンを覚えた後
- 人を表す言葉: 初めて板を履く人、子ども連れ、家族、小さな子ども
- やわらかい語尾: 〜に適しています、〜に向いています、〜に便利です、〜な場合があります
- ゲレンデ以外の実用情報: 駐車場、シャトルバス、徒歩、用具運搬、坂道、動く歩道、そり

「山頂側の急斜面」のような言い方が読みにくかったのは、位置を表す言葉のせいではない。
その文が事実だけで終わっていて、読み手にとって何を意味するかが書かれていなかったからである。

## 3つの欄の役割

同じことを2箇所に書かない。

| 欄 | 書くこと |
| --- | --- |
| `courses` | コース名と、その斜面の様子＋誰が、どの段階で使うか |
| `reason` | そのカテゴリで来た人にとって、このスキー場が何をしやすく、何が負担になるか |
| `full` | 7カテゴリ全体で、行き先選びを最も左右すること |

**コース名は `courses` にだけ書く。`full` と `reason` には書かない。** 見本でも、良い点・
気になる点には「豪円山」「U1コース」が出てこない。エリアの位置（山麓側、中腹）と、誰にとって
どうかで書けば足りる。

`reason` にコースの紹介文を書かない。次は `courses` の内容である。

- 悪い: 「天狗コースは、山頂から続く3.2kmの緩やかな初級コースです。」

## detail.json から落とすもの

`detail.json` の `reason` には、記事に必要な事実がほぼ全部書かれている。次を落とせば残りが
記事の中身になる。

- 年、シーズン、媒体名、投稿者、件数（「2026年2月の子連れ口コミでは」など）
- 引用文と、引用であることを示す表現（「〜と評価している」「〜との声がある」）
- score をその値にした理由（「複数年で確認できるため◎」など）
- 調査範囲の説明（「対象外の◯◯は根拠に含めず」など）

## 書かないこと

- 「人気です」「評価されています」など、評判を事実の代わりにした文
- 「カービングできます」「パウダーを楽しめます」など、カテゴリ名から分かること
- score を言い直しただけの文
- 単日の雪質や偶然の荒れ方
- `detail.json` にない因果関係、条件、数値

`detail.json` が「高評価が1コースに集中している」と書いているとき、「コースは1本しかない」に
変えてはいけない。調査上の確信度と、地形の事実は別物である。

## 手順

1. `detail.json` の `resortId` と7カテゴリを確認する。既存の `article.json` は読まない。
2. カテゴリごとに `detail.json` の `reason` を読み、上の「落とすもの」を落とした残りを、
   事実と意味の組で書き出す。
3. `courses` を書く。`detail.json` の `courses` にあるコースだけを使う。
4. `reason` を2〜5項目書く。良い点と気になる点の両方を残す。
5. `full` を3〜5項目書く。
6. `score`、`warn`、`warnReason` を `detail.json` からそのままコピーする。
7. validator を実行し、article側の警告を0件にする。

```bash
node .shared/skills/review-write-article/scripts/validate-review-json.mjs \
  src/private/data/reviews/<resortId>/detail.json \
  src/private/data/reviews/<resortId>/article.json
```

detail側の警告・エラーはこのskillで直さず、報告だけする。

## 最後の読み直し

validator を通すだけでは足りない。カテゴリ単位で表示順に読み、次を確認する。

1. 各項目に、事実と、それが読み手にとって何を意味するかの両方があるか。
2. 冒頭の見本と並べて、同じ調子で読めるか。硬く短く切り詰めていないか。
3. `full` と `reason` にコース名が入っていないか。
4. `reason` の各項目が、`courses` の説明と別のことを言っているか。
5. 前の項目を読まなくても意味が通るか。「これ」「同じ」「別の」で前を参照していないか。
6. 同じカテゴリの項目同士で、コース数や範囲が矛盾していないか。
7. `detail.json` に書いていない条件や因果関係を足していないか。

引っかかった文は、語句を差し替えるのではなく `detail.json` の記述へ戻って書き直す。

## 変更してはいけないこと

- `detail.json` にない情報を追加しない。外部を調べない。
- `score`、`warn`、`warnReason` を変えない。
- カテゴリを省略しない。`score` に `null` を使わない。
- `label` に `good` / `bad` / `description` 以外を使わない。

## 完了報告

- 作成した `article.json` のパス
- 7カテゴリの `score`
- `warn: true` のカテゴリ
- article側の validator 警告が0件になったこと
- detail側に警告・エラーがある場合は、その件数と内容
