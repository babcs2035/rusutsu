# スキー場レビュー調査・detail.json作成

指定されたスキー場について利用者レビュー・口コミ・体験談を横断的に調査し、7カテゴリごとに **評価（◎○△）・評価理由・コース・出典** を記録した `detail.json` を作成する。

目的は、行ったことのないスキー場の中から行き先を選ぶ人の判断材料を作ること。「上級圧雪とコブを重視する人が、その2カテゴリを見て自分に向いているか判断できる」状態を目指す。

**評価はこの調査の中で行う。** 大量のレビューを読んだうえでしか「この点は多くの人が触れている」「これは誰も触れていない」は判断できないため、評価と評価理由をここで確定させる。

---

# 1. 出力構造

```json
{
  "resortId": "resort-slug",
  "research": { "date": "YYYY年M月D日", "note": "調査全体の状況" },
  "beginner": {
    "score": "○",
    "reason": "評価理由。後述の7要素をすべて含める。長さ制限なし",
    "courses": [
      { "name": "コース名", "description": "そのカテゴリでの特徴と利用者評価", "sources": [] }
    ],
    "sources": [],
    "warn": false,
    "warnReason": null
  },
  "intermediate": {}, "advanced": {}, "moguls": {},
  "powder": {}, "tree-run": {}, "park": {}
}
```

7カテゴリすべてを同じ形で必ず含める。独自キーを追加しない。

## sources の形式

```json
{
  "type": "review",
  "url": "https://...",
  "description": "そのページに何が書かれているかの説明。投稿時期を含める",
  "quote": "原文引用。引用できるものがあれば入れる。なければ空文字"
}
```

- `type` は `"review"`（利用者の声）か `"official"`（公式・自治体・観光協会等の客観情報）
- `official` には引用を求めない。`description` に確認した事実と確認日を書く
  例: `"現行コース・リフト一覧。全4コース・2リフト。パーク記載なし（2026-07-14確認）"`
- `quote` は元ページに実在する文章のみ。**自分の要約を quote に入れてはならない**

---

# 2. score の基準

| score | 基準 |
| --- | --- |
| ◎ | そのカテゴリを主目的に来ても満足できる、と複数の利用者から繰り返し評価されている |
| ○ | 楽しめるが、量・条件・動線・時期などに制約がある。または評価は確認できるが限定的 |
| △ | 対象が少ない、存在しない、またはそのカテゴリを目的に選ばれていない |

`null` は使わない。3値のいずれかを必ず付ける。

**「対象はあるが誰も触れていない」も △。** それは「そのカテゴリ目的では選ばれていない」という情報であり読者に有効。ただし実態を `reason` に正直に書く。

**レビュー件数の少なさだけを理由に評価を下げない。** 小規模スキー場でレビューが少ないのは当然であり、スキー場の質とは別問題。確認できた範囲が良ければ ○ 以上を付ける。ただし ◎ は「繰り返し評価されている」ことが条件なので、1〜2件の好評だけでは ◎ にしない。

---

# 3. reason の書き方

`reason` は記録であり記事の下書きではない。**長さ制限なし。目安400〜1200字。** 以下7つを必ず含める。

1. そのカテゴリで中心的に評価されている点（具体的なコース・エリア名込み）
2. その評価がどれくらいの広がりで確認できたか（何人・何年・どの媒体）
3. 弱点・制約・人を選ぶ点として挙がっているものと、その広がり
4. 意見が分かれる点があれば、その内容となぜ分かれるか
5. 一時的な条件（当日の雪質・混雑・リフト停止）と構造的特徴の区別
6. **その score にした理由**（なぜ ◎ ではなく ○ か、なぜ △ か）
7. 判定に迷った点・確認できなかった点

6を必ず明記する。ここが後工程と人間の確認の起点になる。

弱点が見つからなかった場合は「探したが見つからなかった」と3に書く。**弱点を作り出してはならない。**

---

# 4. 情報源

主根拠は利用者の声とする。スキー場レビューサイト、Google・Yahoo!・楽天トラベル・じゃらん・Tripadvisor等の施設レビュー、個人ブログ、滑走記録、SNS、実際に滑走したことが確認できる体験談。

公式サイト・自治体・観光協会は、正式名称、コース名、圧雪/非圧雪、パークや公式ツリーランの有無、設備の新設・廃止・名称変更、構成が変わっていないかの確認に使う。**公式の宣伝表現を利用者評価の根拠にしない。**

---

# 5. 元ページと文脈

検索結果スニペットだけを根拠にしない。必ず元ページ本文を開く。閲覧できない投稿は使わない。

採用する前に、直前直後・段落全体・必要ならページ全体を確認する。

- 後続文で否定・修正されていないか
- 天候・雪質・時間帯・混雑等の条件付きではないか
- 他コース・他スキー場との比較ではないか
- 対象コースや利用者レベルを取り違えていないか
- 一部の話をスキー場全体へ一般化していないか

**引用自体は存在しても、ページ全体を読めばその意味ではない切り取りを絶対に行わない。** 文脈を確認できないソースは使わない。

---

# 6. 一時的状況

当日の天気・雪質・気温・強風・リフト停止・事故・大会等は恒久評価に使わない。複数年・複数シーズン・複数利用者から同傾向が確認できれば構造的特徴として使える。

パウダーは降雪日の体験自体が重要なので、雪が溜まりやすい場所・残りやすさ・非圧雪コースの特徴を読むために使ってよい。ただし特定日の雪質を恒常化しない。

---

# 7. 用語

- **コブ**: 常設コブ、モーグルコース、シーズン中に継続的に作られる明確なコブラインのみ。単に荒れた斜面や当日だけの凹凸は除外
- **ツリーラン**: 公式に許可・管理された樹間滑走エリアのみ。通常の林間コースと管理区域外のバックカントリーは除外。現在利用可能か最新公式情報で確認する
- **パーク**: キッカー・BOX・レール・ハーフパイプ等の人工アイテムが継続設置される場所。自然地形や一時的なウェーブは原則除外

---

# 8. 7カテゴリの観点

- **beginner**: 歩いて練習できる場所、緩く幅広い斜面、初心者向け林間、他利用者との動線、混雑、コース数、移動、リフト乗降
- **intermediate**: 幅広い中斜面、長距離圧雪、整備、カービング、コース接続、回しやすさ、混雑、バリエーション
- **advanced**: **上級者向け圧雪コースのみ。** 急斜面、高速ロングターン、幅、距離、混雑、回しやすさ。非圧雪・コブ・ツリーランを混ぜない
- **moguls**: 継続的なコブの有無、場所、長さ、掘れ方、ピッチ、難度、複数ライン、維持、回しやすさ
- **powder**: 非圧雪量、降雪後の競争率、残りやすさ、コース脇、狙える場所の数
- **tree-run**: 公式ツリーランの有無、数、広さ、難度、回しやすさ、登録・装備ルール
- **park**: アイテム数、サイズ幅、対応レベル、整備、レイアウト、回しやすさ

各カテゴリで**長所・弱点・具体的コースの3方向**から探す。弱点探索では「悪い」「不満」だけを探さない。advanced なら「上級圧雪が少ない」「急斜面は非圧雪中心」「回せる場所が限られる」「中級主体」等、そのカテゴリを目的とする人にとっての構造的な物足りなさも探す。**ただし公式スペックだけから利用者の不満を推測しない。**

---

# 9. 調査量

目標はスキー場の規模で変える。リフト4本以上なら全体40〜60件、3本以下なら15〜30件の独立利用者ソース。同一人物の複数投稿・転載・コピーを独立ソースとして数えない。

カテゴリ単位の件数目標は設けない。7カテゴリに細分しているため、カテゴリごとの対象が少ないのは正常。

届かない場合は検索語・媒体・年代を変えて追加調査し、それでも不足するなら `research.note` に試した検索語と媒体を書く。**到達しないこと自体は異常ではない。**

`sources` に全件載せる必要はない。広く調査したうえで、代表的で文脈の明確なものを採用する。

---

# 10. warn

カテゴリ単位で付ける。

- `warn: false, warnReason: null` — 十分な根拠がある
- `warn: true, warnReason: "…"` — 人間確認を推奨

`warnReason` には**何が不確かなのかを具体的に書く。**「確度が低いため確認が必要」のような定型文は禁止。

例: `"ぶなコースの圧雪頻度は公式に記載がなく、利用者記録も非圧雪の日に偏っている"`

warn を付ける例。主要な判断根拠が独立1件、情報が古く現行性を確認できない、意見が大きく分かれる、対象の有無自体を確認できない。

元ページ・文脈を確認できない場合は warn で残さず、そのソース自体を使わない。

---

# 11. 手順

1. 正式名称・所在地、現行のコース・リフト、圧雪/非圧雪、コブ、公式ツリーラン、パーク、改修履歴を公式情報で確認する
2. 利用者レビューを広く収集する
3. 各カテゴリで長所 → 弱点 → 具体的コースの順に探す
4. 採用候補の前後・段落・ページ全体を確認する
5. 一時的状況と構造的特徴を分ける
6. 同一人物・転載を除外し、直近5シーズン中心に追加調査する
7. 情報が少ないカテゴリは検索語・媒体を変えて再検索する
8. カテゴリごとに score を決め、`reason` に7要素を書く
9. 全引用を再照合し、JSONとしてパースできることを確認する

---

# 12. 最終確認

- 7カテゴリすべてに `score` / `reason` / `courses` / `sources` / `warn` / `warnReason` がある
- `score` が ◎ ○ △ のいずれか（`null` を使っていない）
- `reason` に7要素すべて、特に**その score にした理由**が書かれている
- `type: "review"` の `quote` が元ページ本文に実在する
- `type: "official"` の `description` に確認した事実と確認日がある
- **自分の要約を `quote` に入れていない**
- `url` が空でない
- 一時的状況を恒久化していない
- advanced に非圧雪・コブ・ツリーランを混ぜていない
- 弱点探索を「酷評探し」に限定していない
- レビュー件数の少なさだけを理由に評価を下げていない
- `warnReason` が定型文になっていない
- JSONとしてパースできる

---

# 最重要原則

**存在しない情報を作らない。同時に、慎重さを理由に調査を省略しない。**

弱点が見つからなければ「見つからなかった」と書く。弱点を作り出してはならない。
レビューが少なければ少ないと書く。それを理由に評価を不当に下げてはならない。

**引用自体は存在しても、ページ全体を読めばその意味ではない切り取りを絶対に行わない。**
